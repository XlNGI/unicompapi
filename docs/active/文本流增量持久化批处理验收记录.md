## 原因

原实现每收到一个 `content_delta` 或 `reasoning_delta`，都会等待 execution 事件完成一次 JSON 与备份原子重写，然后才继续读取上游分片。模型返回大量两三个字符的小分片时，本地磁盘写入会反向阻塞 SSE 消费；模型生成耗时和逐分片保存耗时叠加，表现为其他客户端正常而本地持续变慢。

## 实际修改

新增 execution 级 `ConversationStreamDeltaBatcher`，接在共享文本 linked lifecycle 与原 execution lifecycle 之间：

- 相邻同类型增量有序合并，不跨 `reasoning` / `content` 重排；
- 首个未落盘增量启动 120ms 刷新窗口；
- 单批达到 8KB UTF-8 时立即进入持久化队列；
- 未完成持久化数据达到 256KB 时恢复对上游的等待，形成有界背压；
- 多批写入通过同一串行尾链保持顺序；
- `complete`、`fail`、取消确认和中断在写入终态前统一 seal 并 drain；
- 后台写入失败会拒绝后续追加与终态成功，不静默丢失；
- 对话正文投影仍只消费已经持久化的正文批次，受控 UI 流也仍在仓储成功后发布。

现有 JSON 原子写入、备份、连续 sequence、重放和项目隔离合同保持不变。
