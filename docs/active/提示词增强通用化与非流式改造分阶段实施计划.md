实施分支：`feature/prompt-enhance-generalization`

分支职责：承载提示词增强通用化、项目上下文强制增强规则、非流式文本推理适配器、可复用 UI/宿主接线及对应测试；不修改会话页业务规则，不新增一级页面，不恢复已禁止能力。功能分支完成后保留本地与远程分支，按项目规则合并回 `develop`。

计划性质：工程侧新增计划，不覆盖最终 UI 与开发交接包，也不修改既有权威原件。

## 一、计划目的

将当前专业生图内的提示词增强链路，改造成可复用的通用能力，并明确以下产品规则：

1. 提示词增强固定使用 `text_reasoning`，不在增强 UI 中展示 `text_chat` / `text_reasoning` 切换；
2. 提示词增强使用非流式文本调用，不复用会话页的 SSE 流式响应链路；
3. 项目上下文可以没有；一旦存在已明确选择的项目上下文，增强就是必需步骤；
4. 只有原始输入时，提示词增强保持可选；
5. 上下文和原始输入必须拼接为完整提示词发送给 LLM；
6. 增强完成不创建图片或视频生成任务；
7. 不影响会话页现有的 `text_chat` / `text_reasoning` 选择和流式对话功能。

## 三、冻结产品规则

### 3.1 输入规则

增强输入由三部分构成：

```text
系统优化规则
+
用户明确选择的项目上下文固定版本
+
用户原始输入
```

项目上下文必须使用真实的固定版本快照，不得使用候选列表中的预览文本。

### 3.2 强制/可选规则

```text
contextSnapshots.length > 0
→ 当前宿主必须先完成一次成功的提示词增强

contextSnapshots.length === 0
→ 提示词增强可选
```

“必须增强”表示生成提交前必须存在与当前输入快照匹配的成功增强结果，不表示自动外发或自动创建生成任务。

### 3.3 传输规则

`text_reasoning` 表示模型能力；`stream` 表示传输方式，二者不得混用。

```text
会话页：
  productFeature = text_chat | text_reasoning
  executionMode = conversation_stream

提示词增强：
  productFeature = text_reasoning
  executionMode = prompt_once
```

提示词增强请求必须走 `prompt_once` 专用合同：

- OpenAI Compatible 接口：单条 `user` message，内容为完整拼接提示词，`stream: false`；
- 仅支持 `prompt` 的接口：发送单个 `prompt` 字段；
- 返回普通 JSON，一次性取得最终文本；
- 不进入现有 SSE 收集器。

### 3.4 结果规则

增强结果是“最终提示词候选”，必须保留原始输入和来源追踪。

- 不覆盖 `originalInput`；
- 不自动创建图片/视频 Task；
- 宿主可按自身策略写入系统补充或最终提示词候选；
- 用户确认边界仍然保留，增强完成不等于生成提交完成。

## 四、目标架构

```text
宿主页面
  ↓ 提供原始输入、上下文引用、增强策略、结果写回策略
通用 PromptEnhancePanel
  ↓ IPC
通用 PromptEnhanceService
  ├─ 输入快照与上下文冻结
  ├─ 候选/参数/外发确认
  ├─ 一次性路由令牌与授权
  └─ prompt_once 执行
       ↓
非流式文本适配器
  ├─ OpenAI Compatible: messages + stream:false
  └─ Prompt Endpoint: prompt
       ↓
普通 JSON 结果解析
  ↓
宿主结果写回与生成门禁
```

通用组件不得依赖专业生图类型；专业生图通过适配层提供草稿、上下文和写回逻辑。会话页继续使用现有会话组件和流式适配器。

## 五、分阶段实施顺序

### PR1｜通用领域合同与策略层

目标：先建立与页面无关的提示词增强输入、快照、策略和结果合同。

主要工作：

- 定义 `PromptEnhanceRequest`、`PromptEnhanceContextSnapshot`、`PromptEnhancePolicy`、`PromptEnhanceResult`；
- 明确 `executionMode = prompt_once` 和 `productFeature = text_reasoning`；
- 定义“有上下文必须增强、无上下文可选”的统一判定；
- 定义增强结果与输入快照的匹配关系；
- 定义上下文、原始输入、模型、参数变化后的过期规则。

验收：

- 领域合同不引用专业生图类型；
- 不传上下文时增强可选；
- 存在上下文时可计算出强制增强门禁；
- 会话页合同不发生变化。

### PR2｜非流式文本推理适配器

目标：建立与现有聊天 SSE 适配器隔离的 `prompt_once` 执行链路。

主要工作：

- 新增非流式文本请求/响应合同；
- 为 DeepSeek 和 OpenAI Compatible/NewAPI 路径增加普通 JSON 请求；
- 根据服务商合同选择单条 `user` message 或单个 `prompt` 字段；
- 强制 `stream: false`，不得接受调用方把增强请求改为流式；
- 增加普通 JSON 响应解析、空结果、超长结果、错误结果和未知结果处理；
- 保留凭证安全、授权 claim、幂等键、费用观察和结果追踪。

验收：

- 增强请求不会进入 `consumeDeepSeekStream` 或 `consumeNewApiStream`；
- 会话请求仍然使用原有 SSE 链路；
- 请求体中明确出现 `stream: false` 或 `prompt` 合同；
- 非流式响应可生成单个完整结果。

### PR3｜项目上下文快照接线

目标：将已选择的项目上下文真实快照接入增强准备和提交。

主要工作：

- 读取草稿中的项目上下文引用；
- 通过现有项目上下文快照能力获取固定版本、Hash 和正文；
- 只纳入明确选择且 `includeInPrompt = true` 的上下文；
- 在准备记录中保存上下文快照及其 Hash；
- 将真实上下文数量和内容类别写入外发确认；
- 上下文版本、Hash、原始输入变化时使旧准备令牌失效；
- 增加输入总长度/Token 预算检查，禁止静默截断原始输入。

验收：

- 上下文存在时，发送内容必然包含对应固定版本正文；
- 上下文不存在时，发送内容只包含系统规则和原始输入；
- 上下文变化后旧增强结果不能用于生成提交；
- 外发确认中的 `contextCount` 与实际一致。

### PR4｜通用 UI 与宿主适配层

目标：把专业生图专属面板拆成可复用组件，避免影响会话页。

主要工作：

- 将 `ImagePromptEnhancePanel` 抽象为 `PromptEnhancePanel`；
- 移除增强面板中的 `text_chat` / `text_reasoning` 切换控件；
- 内部固定使用 `text_reasoning` 候选；
- UI 只展示准备、确认、请求、完成/失败等状态，不展示推理过程或流式文本；
- 通过宿主适配层注入原始输入、上下文摘要、策略和结果写回；
- 专业生图保留适配器，继续支持系统补充和手动合并最终提示词；
- 为未来视频或其他创作宿主保留相同接口，不在本 PR 新增一级页面。

验收：

- 专业生图仍可使用增强；
- 有上下文时 UI 明确显示“必须增强”，且生成提交被门禁阻断；
- 无上下文时增强显示为可选；
- `ChatPage` 的模式切换、会话状态和流式输出无变化。

### PR5｜IPC、授权、持久化和生成门禁

目标：把通用合同贯通到 Electron IPC 和宿主生成流程。

主要工作：

- 更新共享 DTO、preload 和主进程 IPC；
- 保留准备/确认/提交分离；
- 保存完整输入快照、路由令牌、过期时间、确认 ID 和执行 ID；
- 请求前失败释放授权，请求开始后按“结果未知”处理；
- 增强不创建图片/视频 Task；
- 有上下文时，生成提交必须引用当前成功增强结果；
- 无上下文时允许用户跳过增强并继续原有生成确认流程。

验收：

- 未完成必需增强时无法提交生成；
- 增强成功不会产生生成 Task；
- 草稿、增强结果、最终提示词和生成任务边界清晰；
- 重复提交、过期令牌和草稿变更均被拒绝。

## 六、关键不变量

1. `text_reasoning` 不决定流式方式，`executionMode` 才决定传输合同；
2. 会话页和提示词增强不得共享可变业务状态；
3. 有项目上下文就必须有当前版本的成功增强结果；
4. 无项目上下文时增强不能被强制要求；
5. 原始输入永不被增强结果覆盖；
6. 上下文正文必须来自固定版本快照，不能来自预览；
7. 增强不创建生成 Task；
8. 远端返回完成不等于正式作品或生成流程完成；
9. 凭证、Token 和原始敏感内容不得进入日志、Git 或环境文件；
10. 非流式增强不得复用 SSE 收集器。

## 八、停止条件

出现以下任一情况时暂停并请求负责人决策：

- 真实服务商接口合同无法确认是 `prompt` 还是 OpenAI Compatible `messages`；
- 非流式普通 JSON 响应结构未得到可靠证据；
- 项目上下文无法取得固定版本正文或 Hash；
- 要求把增强自动创建图片/视频 Task；
- 要求修改会话页为非流式或删除会话能力切换；
- 要求新增一级业务页面、恢复批量创作或恢复首页入口；
- 需要进入阶段 10 的安装包、签名、公证、生产发布或媒体分发范围。

## 九、执行前确认项

负责人审阅本计划时只需确认以下产品决策：

1. 有项目上下文时，生成提交是否必须阻断到增强成功；
2. 增强结果在通用合同中是否定义为“最终提示词候选”，由宿主决定写入系统补充或最终提示词；
3. 真实服务商是否统一走 OpenAI Compatible 单条 `user` message，还是保留 `prompt` 字段适配分支；
4. 上下文过长时采用阻断，还是采用经确认的裁剪策略。

负责人批准后，严格按 PR1 → PR2 → PR3 → PR4 → PR5 → PR6 顺序执行；每个阶段完成并通过验收后，才进入下一阶段。
