# 会话功能企业级修复计划

日期：2026-08-14

状态：PR1「统一执行协调器与真实取消」已在 `feature/chat-execution-coordinator` 实施并通过工程门禁，待代码审查与合并；PR2—PR8 未启动。

## 一、计划基线

本计划不引用既有阶段验收标准，以常见企业级 AI 会话系统的以下要求作为判断和验收基线：

- 正确性：页面状态必须与真实网络请求、持久化执行和调用记录一致；
- 可靠性：取消、失败、退出、断线和重启都有明确结果；
- 一致性：Message、Execution、Invocation、Intent 和 Usage 不得长期互相矛盾；
- 可恢复性：活动执行在页面切换或应用重启后可重新发现，不产生重复提交；
- 性能：长回复和长会话不能因全量轮询、全文件重写和全量渲染持续退化；
- 可观测性：能够区分上游、网络、SSE 解析、本地持久化和 UI 渲染耗时；
- 安全与治理：凭证隔离，远程内容受控，会话数据可按明确语义删除和保留；
- 可测试性：关键结论由跨层集成、故障注入和性能测试证明，不只依赖类型或源码正则。

本计划只修复现有纯文本会话能力，不增加引用、工具、审批或其他业务事件。

## 二、现状结论

当前会话功能可以完成普通文本生成，但还存在以下企业级缺口。

### 2.1 真实取消没有闭环

页面点击“停止生成”后会先把本地 execution 和 assistant message 乐观显示为 `cancelled`，但现有 IPC 只修改 Conversation Message，没有按 `responseExecutionId` 调用 DeepSeek/NewAPI adapter 的 `cancel()`。真实 SSE 请求可能继续运行、消耗上游资源并继续写入本地。

### 2.2 多套状态长期漂移

同一次会话调用同时存在：

- Conversation Message；
- ConversationResponseExecution；
- ProviderInvocationAttempt；
- SubmissionIntent；
- ProviderUsageObservation。

当前会话适配器的 usage 接到空实现，terminal observer 没有接到统一调用记录。回复完成、失败或取消后，调用记录可能仍停留在 `provider_accepted/accepted`，导致任务中心状态、耗时、用量和审计结果失真。

### 2.3 页面切换与应用重启不能恢复活动执行

React 页面只维护一个 `responseExecution`。切换会话后会清空该对象，但后台请求可能仍在运行；返回原会话时没有活动 execution 发现接口，也不能恢复停止按钮和流式读取。

主进程退出只等待短期 IPC 操作，没有统一中断会话 adapter 和保存中断终态。异常退出后，持久化 execution 可能永久停在 `pending/streaming`。

### 2.4 流式链路本地开销过高

正常流式显示依赖 200ms 轮询：

```text
读取完整 execution JSON
-> 解析和校验全部 executions/events
-> 投影完整累计正文
-> IPC 返回完整 DTO
-> React 重渲染消息列表
-> ReactMarkdown 重新解析内容
```

事件追加同时需要读取、解析、备份并重写整个 JSON 文件。现有增量批处理能够减少高频小分片事件数，但不能解决单文件随项目历史增长而产生的线性读写问题。

### 2.5 SSE 兼容和故障诊断不足

当前流解析只接受 `data:` 行，会拒绝标准 SSE 注释心跳或其他已知事件字段；网关返回模型别名或部署名时，也可能因为与请求模型名不完全相等而失败。多种失败最终折叠为通用 `invalid_response`，运行时安全 logger 又没有接入 Electron 生产组合，无法确定具体失败环节。

### 2.6 失败补偿和重试语义不完整

页面先保存 user message，再创建回复草稿、准备路由并提交。后续任一步失败都会留下没有有效 assistant 回复的 user message。页面没有“重试本次回复”，领域已有的 `retryOfExecutionId` 没有形成 UI、IPC 和新 attempt 闭环。

### 2.7 参数和上下文容量控制缺失

文本 ParameterSchema 已定义安全可调参数，但会话页固定提交空参数。历史消息和已选上下文会全部进入请求，没有模型上下文窗口预算、token 估算、裁剪策略或风险提示。长会话最终会在本地上限或上游上下文限制处突然失败。

### 2.8 安全与数据治理边界不足

Markdown 没有明确限制远程图片自动加载，页面也没有完整 CSP。会话“删除”实际是软删除，正文仍保留在项目文件中，缺少永久清除、保留期限和用户可理解的删除语义。

### 2.9 测试不能证明真实闭环

现有领域和适配器测试覆盖较好，但缺少以下跨层证据：

- renderer 到真实 adapter AbortController 的取消；
- adapter 终态到 Message、Execution、Invocation、Intent 和 Usage 的一致收口；
- 应用退出、强制终止和启动恢复；
- 会话切换后的活动 execution 重新发现；
- SSE 心跳、模型别名和错误事件；
- 大项目 JSON、长会话和 Markdown 渲染性能。

## 三、修复目标

本计划完成后必须达到：

1. 停止操作控制真实 provider transport，页面不提前伪造 `cancelled`；
2. 所有终态同步到 Message、Execution、Invocation、Intent 和 Usage；
3. 会话切换、renderer 重建和应用重启后能重新发现活动或中断 execution；
4. 同一会话默认不产生意外并发回复；
5. 正常流式展示不依赖 200ms 全量轮询；
6. 流式事件存储不会随项目全部历史持续线性恶化；
7. SSE 心跳和已登记模型别名不会被误判，失败阶段可诊断；
8. 失败重试复用原 user message，但创建新的 execution 和 attempt；
9. 动态参数和上下文容量在请求前受控；
10. Markdown、外链、删除和保留策略达到本地企业应用的最小治理要求。

## 四、总体技术方案

### 4.1 新增统一执行协调器

新增主进程级 `ConversationExecutionCoordinator`，以 `responseExecutionId` 为唯一键管理活动调用。它负责：

- 注册 provider operation ID、adapter cancel handle 和 completion promise；
- 持有并释放对应 AbortController；
- 调用现有 ConversationResponseExecutionLifecycle；
- 协调 Conversation Message 投影；
- 推进 ProviderInvocationAttempt、SubmissionIntent 和 Usage；
- 处理用户取消、应用退出、transport 中断和启动恢复；
- 防止重复终态、重复取消和同一 attempt 重复提交。

不新增新的业务事件体系，继续使用现有：

```text
execution_created
stream_started
reasoning_delta
content_delta
cancel_requested
stream_completed
stream_failed
stream_cancelled
stream_interrupted
stream_resumed
```

Coordinator 负责确保这些事件与 Message 和调用审计同步，而不是让页面分别修改状态。

### 4.2 明确状态所有权

| 状态 | 权威来源 | 页面权限 |
|---|---|---|
| 回复执行状态 | ConversationResponseExecution 事件投影 | 只读 |
| assistant message 状态和正文 | Execution 投影后的 Conversation | 只读 |
| 上游调用状态 | ProviderInvocationAttempt/Event | 只读 |
| 提交幂等与授权状态 | SubmissionIntent | 只读 |
| 活动请求和取消句柄 | 主进程 Coordinator 内存注册表 | 只能通过命名 IPC 发命令 |

页面只能发送 `submit/cancel/retry/subscribe` 等命令，不得自行把 execution 改成终态。

### 4.3 完善现有状态机

保留现有主要状态：

```text
pending -> streaming -> completed
                    -> failed
                    -> cancelled
                    -> interrupted
interrupted -> streaming/failed/cancelled
```

补强规则：

- `cancel_requested` 必须在 UI 中表现为“正在停止”，不能立即显示 `cancelled`；
- 只有 adapter/transport 确认结束后追加 `stream_cancelled`；
- 用户取消、应用退出和 transport 中断必须使用不同原因；
- completed、failed、cancelled 为不可逆终态；
- 同一 execution 只允许一个终态；
- 用户重试创建新 execution 和 ProviderInvocationAttempt，并写入 `retryOfExecutionId`；
- unknown outcome 不自动重试。

如确需在 Execution DTO 中增加 `cancel_requested` 投影状态，应通过 Schema 版本迁移完成；不得只在 React 中增加临时状态冒充持久化事实。

### 4.4 终态协调顺序

正常完成：

```text
刷新已接受增量
-> 追加 stream_completed
-> 投影 assistant message completed
-> 更新 invocation completed
-> 保存 usage reported/not_reported
-> 更新 submission intent completed
-> 发布最终 DTO
-> 释放活动 operation
```

失败、取消和中断使用相同协调原则。中途写入失败时留下可恢复记录，启动扫描继续协调，不能向页面返回假成功。

## 五、真实取消方案

### 5.1 IPC

新增按 execution 控制的命名接口：

```text
cancelConversationExecution(responseExecutionId)
```

主进程必须核对：

- 当前项目归属；
- execution 是否存在且为活动状态；
- 对应 invocation attempt 和 adapter handle；
- 重复取消是否可幂等返回；
- 已进入终态时不得再次调用上游 cancel。

### 5.2 Adapter 接线

Conversation text dispatch bridge 不再只返回 `providerOperationId`，还要把 operation handle 注册到 Coordinator。DeepSeek、NewAPI 和 UniCompAPI 必须共用同一取消协议：

1. 追加 `cancel_requested`；
2. 调用 adapter `cancel(providerOperationId)` 或 AbortController；
3. 等待 consume completion；
4. 追加 `stream_cancelled`；
5. 更新调用记录和 usage 可用性；
6. 释放活动 handle。

取消请求失败或状态未知时不得显示“已停止”，必须进入明确失败或中断状态。

## 六、调用终态与 Usage 一致性

- 移除会话路径的 `noopUsage`；
- 为 DeepSeek/NewAPI adapter 注入真实 usage repository sink；
- 注入 terminal observer，将 completed、failed、cancelled、interrupted 映射到统一 invocation 事件；
- SubmissionIntent 与 ProviderInvocationAttempt 使用同一个终态协调服务推进；
- usage 未返回时记录 `not_reported`，不能写成 0；
- 响应损坏且是否计费不明时记录 `unknown_outcome`；
- 调用记录详情必须能区分请求未发出、已接受、完成、失败、取消和结果未知；
- Coordinator 启动恢复时检查 Message、Execution 和 Invocation 是否不一致，并执行幂等补偿。

## 七、切换、退出与恢复

### 7.1 活动执行发现

新增安全查询：

```text
listActiveConversationExecutions(conversationId?)
getConversationExecution(responseExecutionId)
```

页面选择会话时先查询活动 execution，再恢复停止按钮、累计正文和流式订阅。同一会话存在活动 execution 时，默认禁止再次发送。

### 7.2 项目和会话切换

- 切换页面不等于取消请求；
- 后台 execution 继续由主进程管理；
- 新页面只读取当前项目 execution，不能串到旧项目；
- 返回原会话时从持久化 sequence 恢复；
- 项目切换时清空 renderer 的上下文选择、候选和 execution 缓存；
- 旧项目仍在运行的调用必须在调用记录中可追踪。

### 7.3 应用退出

退出顺序：

1. 拒绝新会话提交；
2. Coordinator 获取全部活动 operation；
3. 发送 application shutdown interrupt；
4. 有界等待 completion 和持久化；
5. 未确认结果写为 interrupted/unknown outcome；
6. 刷新所有写入后退出。

### 7.4 启动恢复

启动后扫描 `pending/streaming/interrupted` execution：

- 有可恢复同一远端 operation 的明确事实时才 attach；
- 流式文本通常无法恢复同一网络流时，标记为 interrupted；
- 保留已经持久化的正文；
- 给用户提供明确重试入口；
- 不自动重新发起收费请求。

## 八、流式投递与 UI 性能

### 8.1 复用现有受控流通道

复用现有 ControlledConversationResponseStreamChannel 和 replay DTO，不新增业务事件类型。补齐 Electron/preload/renderer 接线：

```text
subscribe(responseExecutionId, afterSequence)
-> replay 已持久化事件
-> 推送后续现有 stream event
-> renderer acknowledge(sequence)
```

规则：

- renderer 按 `executionId + sequence` 幂等消费；
- 超过 in-flight 上限时断开订阅，但不影响 provider 执行；
- renderer 重连后从最后确认 sequence 重放；
- `getResponseExecution()` 保留为初始快照和故障降级，不再每 200ms 调用；
- renderer 断开不能自动取消 provider 请求。

### 8.2 React 渲染

- 历史 Message 和 Markdown 组件 memo 化；
- 只有活动 assistant message 随增量更新；
- 将正文与 reasoning 展示分开更新；
- 对活动 Markdown 使用有界刷新频率；
- 长代码块、表格和超长单词执行布局与性能测试；
- 页面切换回来只重放缺失 sequence，不重新解析不变历史。

## 九、持久化性能改造

### 9.1 短期措施

- 保留现有 120ms/8KB 增量批处理和终态 drain；
- 记录事件文件大小、事件数、写入耗时和投影耗时；
- 避免一次生命周期操作重复读取同一完整文档；
- 将执行快照读取与全量事件校验从 UI 高频路径移除；
- 对慢速、交错 content/reasoning 流验证批处理仍能减少写入。

### 9.2 长期存储 ADR

在代码迁移前建立独立 ADR 和基准测试，对比：

1. SQLite 事务表保存 execution、events 和索引；
2. 分段 append-only journal 加原子快照。

优先选择能够同时通过 Windows Electron 构建、崩溃恢复、并发写入和性能门禁的方案。不得继续让无限增长的全部事件永久依赖单个全量重写 JSON。

迁移要求：

- 旧 JSON 保持可读；
- 导入可中断重试；
- 验证成功前不删除源文件；
- 对比 execution 数、事件数、sequence、终态和累计正文；
- 迁移失败时旧项目只读打开，不覆盖原始数据。

## 十、SSE 兼容和可观测性

### 10.1 SSE 规则

- 接受标准 `data:` 事件；
- 忽略标准注释心跳和空事件；
- 只解析明确批准的其他 SSE 字段；
- 心跳刷新上游空闲计时，但不生成正文增量；
- response ID 校验同一流内一致性；
- 模型名使用精确登记的别名/部署映射，不做任意模糊匹配；
- 上游 error event、畸形 JSON、空完成、无 finish reason 和不支持的 finish reason使用不同 safe code；
- 本地持久化和 UI 渲染时间不计入上游空闲超时。

### 10.2 脱敏指标

每次调用至少记录：

- correlation ID、execution ID 和 attempt ID；
- adapter、协议和安全模型显示名；
- 请求开始、响应头、首个 SSE 事件、首个正文、最后分片和终态时间；
- transport、SSE 解析、持久化和投影耗时；
- 收到分片数、持久化批次数和 renderer 推送数；
- 稳定 safe code、失败阶段和 retryability。

禁止记录 API Key、Authorization、完整 Prompt、完整上下文、原始响应、签名 URL、远端 operation ID 和内部堆栈到普通日志。

## 十一、失败重试、参数和上下文预算

### 11.1 重试

新增：

```text
retryConversationExecution(responseExecutionId)
```

规则：

- 原 execution 必须为 failed/cancelled/interrupted 且允许人工重试；
- 复用原 user message，不重复追加用户正文；
- 创建新的 response draft、execution、assistant message 和 invocation attempt；
- 设置 `retryOfExecutionId`；
- 当前候选、参数和上下文必须重新准备和校验；
- 旧 attempt 永久保留；
- unknown outcome 不开放普通重提，只允许恢复或人工确认。

### 11.2 动态参数

- 按候选 ParameterSchema 渲染安全字段；
- 不写死模型专属参数；
- 参数变化后废弃旧 prepare token；
- temperature/top_p 等互斥规则在主进程再次校验；
- 截断失败提示可以直接定位到 `max_tokens` 控件；
- 点击发送代表本次提交动作时，审计文案不得伪造为额外的独立确认步骤。

### 11.3 上下文预算

- 提交前计算消息数量、字符数和估算 token；
- 读取所选模型已登记的上下文限制；
- 超限时在 HTTP 前失败并给出减少上下文、新建会话或裁剪历史的选择；
- 裁剪必须按明确策略执行并保存快照；
- 不静默删除最近用户消息、system 内容或已明确选择的项目上下文；
- 没有可信模型限制时显示未知，不猜测容量。

## 十二、安全和数据治理

- 增加明确 CSP；
- Markdown 默认禁止远程图片自动加载，或改为用户触发的受控加载；
- 外链继续限制安全协议，并根据企业部署策略增加域名规则或离开应用提示；
- 区分“从列表隐藏”和“永久清除”；
- 永久清除需处理 Conversation、Response Draft、Execution 和不再被引用的相关事实；
- 定义会话、流事件和诊断日志保留期；
- 项目会话文件不得与 API Key 安全仓储混放；
- 企业部署文档补充磁盘加密、目录 ACL、备份和恢复责任边界。

## 十三、实施分支与顺序

每个功能从最新 `develop` 创建独立 `feature/*` 分支，逐支测试和合并，合并后保留本地与远程分支。

- 建立 Coordinator 和活动 operation registry；
- 将 adapter handle 注册到 execution；
- 新增按 execution 取消 IPC；
- 删除页面乐观伪造终态；
- 完成真实 transport 取消集成测试。

### PR2｜调用终态与 Usage 一致性

建议分支：`feature/chat-terminal-consistency`

- 接入 terminal observer；

### PR3｜退出、启动与活动执行恢复

## 十六、完成标准

只有全部满足以下条件才能宣布会话基础修复完成：

1. 点击停止后真实 adapter/transport 被控制，UI 经过请求中和确认终态；
2. 完成、失败、取消和中断不会让调用记录永久停在 accepted；
3. 应用重启后不存在无法解释的永久 streaming；
4. 切换会话后可找回活动 execution，且不会意外重复发送；
5. 正常流式 UI 不再依赖 200ms 全量轮询；
6. 大项目事件追加和 UI 更新通过性能门禁；
7. SSE 心跳不会导致 invalid response，失败阶段可从脱敏诊断确定；
8. 重试创建新 attempt 并保留旧事实，不重复 user message；
9. 参数和上下文限制在 HTTP 前校验；
10. Markdown、外链、删除和保留策略通过安全与数据治理测试；
11. 自动化、构建和 Windows Electron 验收 0 失败、0 非预期跳过。

## 十七、停止和回滚条件

出现以下任一情况时停止当前 PR：

- 取消仍只能改变 UI，不能控制真实 adapter；
- 终态协调可能产生重复提交或重复计费；
- 新推送通道绕过安全 DTO；
- 新存储方案无法通过 Windows 构建或恢复测试；
- 数据迁移需要覆盖尚未验证的源文件；
- 修改范围扩展到图片、视频、工具、引用、审批或发布系统；
- 为通过测试伪造 usage、终态、推理内容或恢复结果。

每个 PR 保持独立回滚边界。新流式推送初期保留快照查询作为降级路径；存储迁移验证成功前保留旧 JSON；状态迁移失败时按旧版本只读打开，不覆盖源数据。
