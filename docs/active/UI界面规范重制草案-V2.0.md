# UniComp UI 界面规范重制草案 V2.0

**状态：** 待项目负责人确认

**起草日期：** 2026-08-19

**适用范围：** UniComp 桌面端所有新建、重做和修改的界面

## 1. 定位与生效规则

本文件用于重新制定 UniComp 的 UI 界面规范，不以既有 UI 交接包、历史截图、旧页面结构或旧视觉 Token 为设计约束来源。

在项目负责人将本文状态改为“已批准”前，本文仅作为重制草案，不自动触发页面、路由、组件或样式修改。批准后，本文及后续批准的页面规格成为 UI 决策的唯一依据；与其冲突的旧 UI 文档仅保留审计价值。

本规范只约束界面、交互、可访问性与验收质量。产品功能范围、数据安全、平台能力和发布流程由项目负责人另行决定，不从旧 UI 资料自动继承。

## 2. 新规范的目标

新 UI 应满足以下目标：

- 用户在任何页面都能明确知道当前位置、当前对象、可执行动作和动作结果。
- 同类任务使用同一组件语义、交互模型和状态表达，不按页面随意变体。
- 视觉层级服务于完成工作，避免把工作台做成营销页、聊天页或设置后台。
- 页面在 Windows 与 macOS 上保持同等的信息架构、可读性和核心操作能力；仅系统窗口控制和平台原生行为可有差异。
- 页面只显示已实现、可执行或可解释为不可执行的能力，不以占位数据、虚假进度或隐含默认值误导用户。

## 3. 强制界面约束

### 3.1 信息架构

- 一级导航、二级导航、页面名称、页面用途和默认落点必须在页面规格中明确声明后才能实现。
- 一个页面只承担一个主要工作目标；跨页面跳转必须保留来源、草稿和未保存修改的处理结果。
- 不能为了兼容窄窗口删除关键信息或主操作。应使用折叠、抽屉、分段布局或纵向滚动，并保持可发现性。
- 页面不得通过隐藏入口、自动跳转或静默改写用户选择来改变工作上下文。
- 未获批准的一级入口、二级入口、模式、步骤条和悬浮工具栏不得新增。

### 3.2 视觉与布局

- 每个页面必须有明确的内容层级：页面标题、当前上下文、主要内容、次要信息和反馈信息不得互相竞争。
- 颜色、字体、间距、边框、阴影、圆角和动画必须使用批准后的设计 Token；页面样式不得私自定义颜色或尺寸体系。
- 状态不能只依赖颜色。成功、警告、错误、禁用、只读和选中状态必须同时具备文字、图标或结构差异。
- 文本不得被截断为无法判断含义的内容。必要时允许换行、中间省略加工具提示或在详情中完整展示。
- 固定工具栏、底部操作区和覆盖层不得遮挡当前页面的可交互内容或键盘焦点。
- 装饰元素不能压过工作内容，动画不得妨碍阅读、输入、拖放或状态判断。
- 默认采用简洁信息密度：页面、卡片和步骤标题只保留完成当前工作所需的信息；重复的流程说明、静态引导和调用记录说明应折叠或隐藏。
- 简洁模式不得隐藏用户输入、用户可执行操作、表单标签、错误原因、授权与费用事实、文件状态、不可逆影响或恢复路径。

### 3.3 组件与操作

- 同一语义的操作必须使用同一组件类型、图标、文案和危险等级。
- 每个操作区最多一个视觉主操作；次要、低频和危险操作必须降低权重或收入菜单。
- 图标按钮必须具有可访问名称和悬浮提示；仅图标不得承担难以猜测的业务动作。
- 按钮、输入、选择器、列表项和拖放目标必须定义默认、悬停、按下、焦点、选中、禁用、加载、错误和只读状态，明确不适用的状态除外。
- 禁用必须说明原因或提供可达的原因说明；加载必须反映真实进行中的动作并阻止重复提交。
- 删除、覆盖、外发、清除和其他不可逆或高影响操作必须经过明确确认，确认层必须说明对象、影响范围和可取消路径。
- 长文本编辑、参数编辑和任务操作不得伪装成聊天消息或使用聊天输入框承载复杂表单。

### 3.4 数据、状态与反馈

- UI 只能呈现实际数据、明确状态或清晰标注的空状态，不得伪造结果、进度、耗时、价格、数量、可用性或成功状态。
- 异步工作至少区分：未开始、进行中、成功、失败、取消、结果未知和需要用户处理；具体状态由页面规格定义。
- 成功反馈必须对应可验证的结果；远端响应、文件下载、本地保存和作品登记等不同阶段不得混写为同一“完成”。
- 页面级持续问题使用可见状态条或内联提示，不能只通过短暂 Toast 呈现。Toast 仅用于不影响后续判断的短反馈。
- 错误反馈必须说明发生位置、已完成部分、影响范围和可执行的下一步，不以错误码替代用户可理解的说明。

### 3.5 可访问性与输入方式

- 所有功能必须可通过键盘到达和操作，焦点顺序与页面视觉顺序一致。
- 焦点状态在深色和浅色主题下均清晰可见，不能被容器裁切或动画隐藏。
- 表单控件必须有可读标签；占位符不能作为唯一标签；错误信息必须关联到对应控件。
- 交互目标的尺寸、间距和文本对比度必须满足批准后的可访问性基线。
- 拖放、悬停和手势操作必须提供键盘或菜单替代路径。

### 3.6 平台与窗口适配

- 关键页面至少覆盖项目定义的最小、常用和宽屏窗口尺寸；不得出现无意义的横向滚动、控件重叠、内容越界或无法到达的操作。
- Windows 与 macOS 的窗口控制安全区、系统快捷键、菜单行为和文件选择行为必须各自验证；不能以一种平台的截图替代另一平台的验收。
- 窄窗口下的布局变化必须保持当前编辑内容、选中项和滚动位置，除非用户主动取消或离开。
- 动画和视觉效果在降低动态效果偏好下必须降级，不影响状态表达。

## 4. 页面规格的最低交付物

任何页面或较大界面改动在实现前，必须至少补充以下内容：

1. 页面名称、目标用户、主要工作目标和进入条件。
2. 信息架构位置、导航名称、路由或打开方式、默认状态。
3. 布局说明：区域、优先级、窄窗口行为和固定区域。
4. 组件清单：组件职责、变体、操作文案和图标语义。
5. 状态矩阵：空白、加载、成功、失败、禁用、只读及该页面特有状态。
6. 数据来源与更新规则：哪些值真实、哪些值未知、何时失效、如何恢复。
7. 高影响操作的确认内容、错误恢复方式和不可逆影响。
8. Windows/macOS 差异、键盘操作和辅助技术要求。
9. 验收截图或原型、自动化测试范围及人工验收项。

没有上述规格的页面，不得以“补 UI”“微调样式”名义直接进入实现。

## 5. 视觉 Token 与组件库重建

- V2.0 Token、主题和基础组件在项目负责人确认前不得直接替换现有全局样式。
- Token 必须先定义语义层，再定义组件层；业务页面只能引用语义 Token 或组件 Token。
- 每个组件必须有用途、禁用用途、属性、状态、可访问名称及响应式约束。
- 新组件应优先扩展已批准的基础组件；需要新增组件时，必须先说明现有组件为何不能表达该语义。
- 页面不得复制一套近似组件以规避公共组件约束。

## 6. 变更与例外

- 项目负责人对本规范的最新明确决策优先于本文任何条款。
- 变更申请必须记录变更原因、涉及页面、组件或 Token、兼容影响、验收方式和生效日期。
- 紧急修复可以先处理阻断性可用性问题，但必须在同一工作项中补齐规格和验证记录。
- 未经明确批准，开发者不得把历史页面、历史截图、第三方产品样式或个人偏好作为恢复旧规范的理由。

## 7. 验收门禁

UI 变更提交验收前必须确认：

- 页面规格与实际实现一致，且没有未批准的入口、组件或交互。
- 关键流程的正常、空白、加载、错误、禁用和只读状态均已验证。
- 键盘导航、焦点可见性、文案完整性、窄窗口布局和主题表现已验证。
- Windows 与 macOS 的验收状态分别记录；未执行的平台必须标为未执行，不能标记为通过。
- 自动化检查、构建和适用的人工界面验收均有真实结果；失败项、例外项和延期项可追溯。

## 10. 实施与验收记录

**实施范围：** 快速生图、专业生图、快速视频、文生视频、图生视频。

- 已实现统一的双区工作台：左侧为可独立滚动的参数与提交区，右侧为生成状态、预览和结果区。
- 文生视频与图生视频已将提示词编辑移入左侧参数区，右侧不再混合参数输入与结果展示。
- 窄窗口下双区回退为纵向布局，参数区恢复为页面滚动，不删除控件或结果内容。
- 已通过 `tsc -p tsconfig.app.json --noEmit`、`node --test` 定向 UI 契约 42 项和 `pnpm.cmd run build`；`git diff --check` 通过。
- 本地浏览器预览未加载 Electron 预加载桥接，因未打开项目只展示前置空状态，无法在该预览中人工核验实际参数/结果工作区。Windows Electron 可视化验收待在具备本地项目能力的桌面运行时执行。
- 已启用全项目默认简洁密度：隐藏重复页面副标题、创作卡片说明、专业工作区步骤说明与调用记录说明；保留用户内容、状态、错误、授权、费用和风险提示。
