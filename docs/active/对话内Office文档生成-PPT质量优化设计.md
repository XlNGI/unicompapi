# 对话内 Office PPT 质量优化设计

日期：2026-08-26
状态：设计已由项目负责人确认并进入实现；2026-08-27 按负责人要求补充 Application 业务编排和单次模型响应后的本地恢复边界。

## 1. 目标与范围

面向办公人员，将对话内 PPTX 从“每节一页、短要点、常见大面积空白”提升为可直接用于工作汇报的固定 16:9 演示文稿。用户输入提示词后，模型生成详细、可校验的结构化大纲；主进程依据页面语义、模板和内容容量确定排版、续页并生成 PPTX。

本轮只优化现有 PPT 生成链路：

- 提供五个原创本地模板：工作汇报、自然简约、极简商务、科技风、融资演讲稿。
- 用户可显式选择模板；未选择时按原始提示词自动匹配，无风格信号默认工作汇报。
- 以“结论、解释、依据或行动”的信息层次替代每页三个短词的规则。用户提供的三个 PPTX 和融资演讲稿 PPTX 仅用于总结视觉规律；不复制其文字、图片、商标、母版或 OOXML 内容。
- 内容超过版式容量时自动拆为续页；不截断、不把字号缩小到可读下限以下、不用无意义留白填满画布。
- 最终文件固定 16:9；浏览器窗口尺寸只影响预览控件整体缩放，不改变生成文件的换行、列数、页面结构或文本内容。

明确不做：URL 读取、扩大 RAG 或附件外发范围、真实 Provider 调用、新图片或视频入口、上传 PPTX 的自由样式迁移、Office 以外格式的排版重构、打包发布和 macOS 支持。

## 2. 现状根因

当前 PPT 内容少和空白多不是浏览器窗口造成的，而是生成链路同时存在以下限制：

1. `src/pages/chat/documentDrafting.ts` 的 PPT 提示词将每页限制为最多 3 个要点、每点 15 字，模型从源头只能输出极短内容。
2. `src/platform/documents/office-document-generator.ts` 按一个 section 固定生成一页，未基于语义和容量拆分或组合页面。
3. 生成器对溢出文本直接使用 `slice` 截断，长内容既不能续页，也不能完整保留。
4. `src/platform/documents/document-layout.ts` 已有局部布局判断，但生产 PPT 渲染没有使用它来决定版式和容量。
5. 文件直接写到最终路径，未采用临时文件、复读校验和原子替换；这会放大取消和写入失败时产生半成品的风险。
6. 模型结构化输出具有非确定性；严格 JSON 偶发缺逗号或括号时，旧 Renderer 又发起第二次模型修正，两次都可能失败，并让 UI 承担了业务编排。

因此，单独在前端调整预览缩放或增大字体无法解决问题。必须同时调整大纲合同、主进程分页排版和模板渲染，且由主进程作为唯一版式决策 owner。

## 3. 已确认的产品规则

### 3.1 模板与选择

PPT 生成入口只显示五个本地模板。工作汇报为默认模板；融资演讲稿是专项模板，其余四个为通用模板。上传 PPTX 仍可作为内容资料解析，但不再充当第六种版式来源，保证生成结果可复现、可测试，也避免把参考文件版权内容带入新 PPTX。

| 模板 | 视觉方向 | 典型用途 |
| --- | --- | --- |
| 工作汇报 | 清晰蓝灰、重点突出、信息密度稳定 | 周报、项目总结、管理层汇报 |
| 自然简约 | 柔和留白、自然绿色、图文均衡 | 培训、文化、方案说明 |
| 极简商务 | 黑白灰与单一强调色、理性克制 | 客户汇报、咨询、复盘 |
| 科技风 | 深色背景、网格和高亮线条、数据感 | AI、数字化、技术方案 |
| 融资演讲稿 | 深色标题带、青色强调、叙事节奏强 | 路演、融资、资源争取 |

### 3.2 内容合同

模型只输出受控 JSON。每个内容页必须表达一个明确结论，并以 3 至 5 个带短标题和解释文字的内容组支撑结论；可选地包含可靠数据、表格、图表或行动项。封面、章节过渡页、数据图表页和结尾页使用与内容页不同的密度规则。

模型不得编造用户业务数据。资料充分时可引用事实和数值；资料不足时生成建议、假设或待确认项，不能虚构业绩、客户、预算或收益。短提示词可以生成完整方案型演示文稿，但不能表述为既有事实汇报。

### 3.3 排版和分页

主进程根据页面语义、模板支持的布局、内容块类型和容量，在封面、结论、要点、双栏、流程、数据、图文和结尾布局间确定性选择。一个 section 可以拆成多张内容页；续页保留原主题并标注“续”。所有输入文本都必须出现在某张生成页中。

标题、分组标题、正文和注释都有模板定义的字号下限。单个内容块超过可读容量时返回受控错误，而不是静默缩小、裁剪或丢弃。图表和表格使用专用页面布局，不能与超量正文重叠。

### 3.4 文件和状态机

保留 `DocumentGenerationRunner -> 文件校验 -> Work 登记` 链路。生成器先在 `files/documents/` 同目录写入临时文件；重新读取并校验文件类型、大小和 Hash 后，再原子替换最终文件。校验或替换失败时不得登记 Work，临时文件必须清理或明确可清理。

同一 assistant message、输出格式和模板的重复请求必须合并；不同模板不得误复用。取消在开始、排版、临时写入、校验和登记之间均可观察，并返回安全、可展示的状态。

## 4. Owner 与调用链

```text
ChatPage（只提交意图、选择 PPT 模板和展示状态）
  -> 受控 document-generation IPC DTO / preload
  -> DocumentGenerationController（DTO、用例调用、安全错误映射）
  -> DocumentGenerationApplicationService（等待终态、编译/本地恢复、指纹、去重、取消、生成和结果挂接）
  -> Platform compiler / recovery adapter（PPT 语义解析与同一响应的局部结构恢复）
  -> DocumentGenerationRunner（文件状态机、取消、校验和登记）
  -> 模板注册表 + 版式/分页器
  -> office-document-generator（pptxgenjs 原生可编辑对象）
  -> FileReference / Hash / Work / 对话文档卡片
```

Renderer 不决定页面结构、编译恢复、去重或写文件；模型不决定模板、路径、权限、费用、重试或成功状态。一次模型响应后，PPT 严格编译失败只允许由 Platform 从同一内容本地恢复，不追加第二次 Provider 调用；不新增第二条 PPT 生成或文件登记链路。Provider 路由和附件外发确认不在本轮修改。

## 5. 结构合同

在既有 `DocumentOutline` 上为 PPT 增加可选页面语义，Word 和 Excel 保持原有解析结果：

```ts
type PresentationPageKind =
  | 'cover'
  | 'section'
  | 'insight'
  | 'comparison'
  | 'process'
  | 'data'
  | 'image_text'
  | 'closing';

interface PresentationSectionMetadata {
  readonly pageKind?: PresentationPageKind;
  readonly takeaway?: string;
  readonly action?: string;
}
```

`pageKind` 只是模型建议；解析器、模板注册表和版式容量策略拥有最终决定权。旧 JSON 和 Markdown 回退继续解析为普通 section。PPT 总文本量、内容组数和最终页数由单一资源策略限制，超限返回结构化错误，不进入生成器。

IPC 只新增 `presentationTemplate?: PresentationTemplateId`。它仅接受五个枚举值，且只在 `kind === 'ppt'` 时有效；旧请求缺少该字段时映射为工作汇报模板。Renderer 不传绝对路径、模板文件路径、任意颜色对象或布局坐标。

## 6. 失败和安全规则

新增或细化的用户可见错误包括：非法模板、PPT 大纲超过资源上限、单个内容块不可读、布局无法容纳、生成已取消、临时文件写入或原子替换失败。内部异常、绝对路径、模型原始输出和堆栈不进入聊天页面。

本轮触及模型不可信输出、IPC 字段、文件写入、资源限制和并发，必须覆盖对应拒绝、本地恢复失败、取消、重复点击和文件登记负面测试。内部 Provider prompt 与用户可见 `displayContent` 必须分离，assistant 结构化 JSON 不直接渲染到聊天页。附件传给模型的范围保持当前行为，不借“内容更丰富”扩大 2,000 字预览或默认启用 RAG。

## 7. 验收标准

1. 五个模板均可从对话页选择并生成真实可打开的 PPTX，且模板 XML 或渲染特征可区分。
2. 同一长大纲的全部正文块、表格和图表都出现在 PPTX 中；溢出通过续页处理，不再由 `slice` 截断。
3. PPTX 固定为 16:9；窄窗与宽窗以相同固定输入生成相同页面结构和文本。
4. 短标题保持单行，长标题在安全区域内换行；正文不低于模板下限，无非预期重叠、裁剪或大面积无意义空白。
5. 非法模板、超限大纲、取消、写入失败、Hash/类型/归属失败和并发重复请求都有可验证结果。
6. Windows Electron 人工验收覆盖五模板、不同窗口、重复点击、取消、文件打开、Hash/类型/归属登记和关闭后的进程残留。
7. PPT 生成只消费一次模型响应；缺逗号等可恢复结构错误通过 Application 调用本地恢复继续生成，Renderer 不展示修正提示、不发起第二次模型调用，内部 prompt/JSON 不进入用户气泡。

## 8. 2026-08-27 多页结构差异与 Office 自然语言修订补充设计

### 8.1 问题证据与设计原则

现有五模板虽然拥有不同颜色、边框和装饰，但多数正文最终统一进入 `renderTextPage -> drawContentUnits`，连续 insight 页的内容组首坐标完全一致。用户截图中的“结论条 + 2×2 内容组 + 行动条”连续复用属于生成器几何结构同质，不是模板配色问题。

参考 [OpenBeetles《搭建前端项目架构》](https://blog.openbeetles.com/98.html) 的可复用原则，本项目采用“统一视觉语言 + 内容驱动的不同构图”，而不是复制参考页面或为每个模板复制一套生成器。模板继续集中拥有颜色、字号下限、容量和构图序列；生成器依据页面语义、内容组数量、字符量和相邻页构图确定性选择结构。

新增的正文构图为 `editorial | split | cards | timeline`：

- `editorial`：大结论与扁平内容层级，适合判断、机会和策略；
- `split`：左侧主张、右侧依据，适合比较或需要强化结论的页面；
- `cards`：保留原有高信息密度结构，作为工作汇报等场景的一种选择而非唯一结构；
- `timeline`：横向步骤或阶段，适合 process 和短内容序列；
- data、image_text、section、closing 保持专用结构。

连续正文页不得使用同一构图；同样内容和模板必须得到可复现序列。模板之间使用不同构图顺序，仍共用一个渲染器和同一容量/分页 owner。

### 8.2 Office 请求计划与修改语义

自然语言触发从 Renderer 关键词判断上移到 Application `analyzeOfficeRequest()`，只输出 `chat` 或受控 `document` 计划。document 计划包含 `action: create | revise`、`documentKind`、可选 `targetDocumentKind` 和 `missing`。它只决定进入哪条已有文档链路，不决定 Provider、权限、路径、费用、重试或成功状态。

规则保持确定性和保守：

- “做/生成/写 + 明确 Word、Excel、PPT”识别为新建；缺少主题或数据范围时先提示补充；
- “把刚才的 PPT 第二页改成时间线”等明确格式修改，或存在上一版文档时“第二页换成时间线”等上下文修改，识别为 revise；
- revise 只选当前会话最近一份同类型已完成文档，不跨项目、不猜测其他格式；找不到目标时停止并提示；
- “PPT 应该怎么做”“分析这份 PPT 为什么单调”等问题仍是普通聊天，避免把讨论误触发为付费生成；
- 用户显式选择的文档类型覆盖自动格式补全，但不能把 create 静默改为 revise。

聊天输入区新增“Office 操作预览”，在发送前显示新建/修改、格式、上一版目标和待补信息。页面只展示 Application 计划，不持久化新的业务状态；发送后仍复用一次模型响应、Application 编排、主进程生成、文件校验与作品登记链路。

### 8.3 新增验收标准

1. 同一模板四个连续 insight 页至少出现三种几何结构，且相邻页不重复；五模板的结构序列可区分。
2. process 页优先时间线，comparison 页优先左右分栏；数据和图文页继续使用专用布局。
3. Word、Excel、PPT 的明确新建、显式修改和基于上一版的上下文修改可被结构化识别；提问/分析不误触发。
4. 缺格式、缺主题/数据范围或缺同类型上一版时不得发起文档模型请求。
5. create 不自动携带最近文档；只有 revise 才把同类型最近文档作为上一版，避免新建需求误改旧文档。
6. 输入区在桌面和窄桌面显示动作、格式、目标及待补信息；键盘发送与原有加载、取消、失败、重复点击行为保持不变。
