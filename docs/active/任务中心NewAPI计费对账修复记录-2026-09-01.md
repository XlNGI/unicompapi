# 任务中心 NewAPI 计费对账修复记录

日期：2026-09-01

## 目标与边界

- 修复任务中心当天消费与供应商占比口径不一致，以及新图片调用后旧视频费用消失的问题。
- 计费组件只汇总已经记录的本地调用，并优先用 NewAPI 使用日志中的实际 `quota` 对账；没有实际账单时才按当前站点价格估算。
- 不修改中转站源码，不修改历史项目 JSON，不发起真实模型调用，不伪造缺失的请求 ID 或账单。

## 根因证据

1. 左侧是近 7 日趋势，右侧此前却聚合近 7 日全部供应商金额；产品要求右侧显示当天消费，因此两边统计周期不同。
2. NewAPI 的 `/api/log/token` 在 `D:/UniComp-new-api/model/log.go` 中按 `id desc` 查询并限制为 `common.MaxRecentItems`，它是最近日志窗口，不是完整历史账单。用新窗口整体替换旧快照时，新图片日志可能把较早视频账单挤出窗口。
3. 账单日志请求曾返回 `429 rate_limited`。原实现把请求失败降级为空日志，刷新时会暂时清空已经对账的费用。
4. 退款曾作为负金额混入消费总额，但供应商占比会过滤非正金额，造成两张图金额口径不一致。
5. NewAPI 异步任务退款日志的 `quota` 是正数，`request_id` 为空，关联远端任务 ID 位于 `other.task_id`。旧解析器强制要求 `request_id`，因此退款行被直接丢弃；旧聚合还错误假设退款额度为负数。

## 修复语义

- 右侧供应商人民币消费占比只聚合上海时区当天，与左侧当天柱金额使用同一批正向消费记录。
- 退款独立统计，不混入消费总额、时间桶和供应商占比。
- 异步视频原扣费按提交 `request_id` 对账，退款按本地已保存的远端任务 ID与日志 `other.task_id` 精确关联；部分退款从原扣费中扣除形成净消费，退款额仍单独累计。缺少精确 ID 时不按模型、时间或金额猜测关联。
- 每次成功取得的最近日志窗口按账单行指纹去重合并到进程内最后有效快照，再按 `request_id` 汇总消费与退款；请求失败或响应畸形时保留已有快照。
- 本地 Invocation、Usage、Route 或结果事实变化仍会触发刷新；同一次摘要构建只共享一个账单上下文，不对每条调用重复请求。

## 验收与未验证边界

- 自动化必须覆盖：当天供应商金额等于当天时间桶金额、近 7 日总额可与当天金额不同、单条畸形日志不清空账单、429 不清空旧账单、最近日志窗口变化不移除旧视频账单、消费与退款分处不同窗口时仍正确合并。
- 新增部分退款回归：原扣费 `¥13.14`、退款 `¥7.4162` 时，净消费、当天时间桶和供应商占比均为 `¥5.7238`，退款汇总为 `¥7.4162`。
- 需在加载新代码的 Windows Electron 中人工验证：先生成视频并确认费用，再生成图片，确认视频与图片费用同时保留；当天柱状金额与右侧供应商金额一致。
- 未进行真实 Provider 调用；服务商后台最终扣费金额及跨应用重启后的历史窗口覆盖度仍需人工对照。进程内快照不会写入项目数据。
