# 诊断日志通道补齐方案

日期：2026-09-24
分支：`feature/diagnostic-logger`
阶段：阶段 9 收口后的稳定性维护；阶段 10 未启动

## 1. 结论

不新增日志产品，不引入云端采集。沿用设置页「日志与诊断」已有的本地分类、级别、滚动、脱敏和诊断包，补一层结构化写入门面，并把当前空转的类别接到真实事件。

业务事实继续留在原位置：

- 任务中心调用记录（Provider Invocation）
- 对话生产 Trace
- 文档任务 Observation

诊断日志只记录进程、发送前门禁和服务商安全事件，供本机排查。

## 2. 范围

本轮实施：

1. Platform `DiagnosticLogger` 事件目录：只接受白名单 `code` 和标量 `facts`
2. `DiagnosticsService.writeEvent` 写入现有分类文件，沿用滚动、级别开关和脱敏
3. 主进程未捕获异常 / 未处理 Promise 拒绝 → `crash.log`
4. NewAPI 安全日志从整段 JSON 字符串改为结构化事件；失败写入 `network.log`，开始/完成写入 `application.log`（debug/info）
5. 对话发送前被门禁拦截（候选不可用、运行授权拒绝、附件门禁等）→ `application.log`，`chat.request_blocked`

明确不做：

- 渲染进程任意写日志
- 在界面展示日志原文或绝对路径
- OpenTelemetry / Sentry / 自动上传
- 把 autosave、图片接收、renderer-trace 散落文件迁入（下一轮）
- 包装全部 IPC handler
- 记录 Token、Prompt、路径、堆栈、原始网页、思维链

## 3. 事件合同

每条日志一行 JSON：

```text
{"at":"<ISO>","category":"application","level":"warn","code":"chat.request_blocked","facts":{"reason":"candidate_unavailable"}}
```

| code | category | level | 允许 facts |
| --- | --- | --- | --- |
| process.uncaught_exception | crashDiagnostics | error | name |
| process.unhandled_rejection | crashDiagnostics | error | name |
| provider.request_started | application | debug | operation, method |
| provider.request_completed | application | info | operation, method, status, elapsedMs, requestBytes, requestId |
| provider.request_failed | networkErrors | error | operation, method, status, errorCode, elapsedMs, requestBytes, requestId, upstreamCode, upstreamType |
| provider.runtime_disposed | application | info | （无） |
| chat.request_blocked | application | warn | reason |

未知 code、未知 fact 键、超长或非标量值一律丢弃，不写文件。日志写入失败不影响主流程。

## 4. 验收

- 定向测试覆盖：事件规范化、类别映射、敏感字段不会进入 facts、级别/分类开关、writeEvent 落盘
- 现有 B4 诊断服务与设置控制器测试仍通过
- 主工程 TypeScript、相关 ESLint、`git diff --check`
- 不调用真实模型、不读取凭证、不产生付费请求
