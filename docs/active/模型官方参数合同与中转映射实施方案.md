# 模型官方参数合同与中转映射实施方案

日期：2026-08-26

当前阶段：阶段 9 已收口后的缺陷修复与后续方案设计；阶段 10 未启动。

状态：已批准方案，尚未开始实现。

## 目标与边界

本方案只对齐模型的**请求体**：请求路径、字段名、值类型、必填性、枚举、取值范围、互斥/依赖关系和明确的默认值。任务查询、结果解析、计费、重试和 UI 以外的服务商功能不在本方案内。

目标是在模型官方文档有可复核依据时，让同一官方模型在官方服务商和经过明确验证的中转路由上使用同一份参数合同；动态参数 UI 从该合同产生必填标记、适用控件和提交前校验。

以下内容不允许推测：

- 不根据模型名称推断官方请求体、必填项、默认值或枚举。
- 不因某个 OpenAI 兼容地址可连通，就假定其接受官方扩展字段。
- 不为必填枚举自动选择第一个值；用户必须显式选择，除非官方文档明确默认值且合同明确记录该默认值。
- 不再以“其他参数”承载一个已知的官方字段。该文案仅是当前表单的未知分类回退，不能作为合同分类。

## 已知问题

目前 NewAPI 视频模型在 `src/platform/providers/newapi/newapi-contracts.ts` 中共用泛化参数模式。字段多为可选自由输入，无法表达每个模型的必填项和枚举，因此现有动态表单虽已具备必填渲染与校验能力，却没有可靠的数据源。

`src/platform/providers/newapi/newapi-video-adapter.ts` 会把部分参数聚合进通用 `metadata`。对于已经有官方合同的模型，这条聚合路径不能再作为 UI 字段来源，否则会丢失字段语义、约束和可选值。

Seedance 的特殊序列化目前仅在 UniCompAPI 包和精确模型键范围内生效。这是正确的最小边界，不能改成“模型名相同即对所有中转站发送 Seedance 官方扩展字段”，因为未完整适配的 OpenAI 兼容中转站可能拒绝字段、静默忽略字段，或用不同语义解释字段。

## 合同和映射模型

每个可适配的官方模型都建立一个版本化的 `OfficialRequestContract`，至少包含：

- 官方模型规范键、产品能力（文生图、图生视频、文生视频等）和官方文档证据链接/版本日期；
- 请求方法和路径，以及模型名放置位置；
- 所有请求字段的 JSON 路径、类型、必填性、默认值、枚举、数值范围、数组限制和字段依赖；
- 每个字段的 UI 暴露级别和控件类型；
- 官方请求体序列化器及其单元测试样例。

服务商中的模型记录不直接复制合同，而是以 `ProviderModelMapping` 指向一个官方规范键，并声明该路由的传输模式：

| 模式 | 适用条件 | 请求体行为 |
| --- | --- | --- |
| `official_passthrough` | 已有该中转站、端点和模型组合的官方或中转站书面兼容证据，以及实际探测/回归证据 | 使用对应官方合同的路径和请求体 |
| `gateway_contract` | 中转站只声明通用 OpenAI 兼容或自行定义的请求合同 | 使用该中转站独立合同，不透传官方扩展字段 |
| `unverified` | 模型名可关联到官方模型，但没有足够的端点与字段兼容证据 | 不能生成可提交候选；提示需完成映射验证 |
| `unsupported` | 已确认不支持能力、端点或必需字段 | 不提供该能力候选 |

模型名称相同只允许进入“待核对”的候选关系，不自动得到 `official_passthrough`。这回答了 OpenAI 兼容中转站未完全适配官方参数时是否会报错的问题：若错误地发送官方请求体，确实可能报错或产生错误结果；本方案通过显式映射把该路由留在 `gateway_contract`、`unverified` 或 `unsupported`，避免错误透传。

## 动态参数 UI 标准

动态表单由所选候选的已解析请求合同生成，而不是由通用 `metadata`、模型名称规则或自由文本字段生成。

- `required=true` 的字段显示必填标记；空值、格式错误、越界值、非法枚举和不满足依赖条件时显示字段级错误。
- 点击“生成/提交”前在前端复核全部可见字段；有错误则阻止 IPC 请求，并将焦点/错误信息定位到第一个错误字段。
- 有官方枚举的字段使用下拉菜单、分段控件或其他有限选项控件，不使用可任意输入的文本框。例如每个模型的分辨率只呈现该合同声明的分辨率集合。
- 布尔、数值、数组、对象和文件引用使用与字段类型对应的控件和解析器。前端校验不替代后端校验，适配器仍须拒绝非法请求体。
- 未有官方合同的字段不得假装为官方必填项或枚举；应保留为中转合同字段，或把候选标记为 `unverified`。

## 实施顺序

1. 建立模型清单：从已注册服务商、可用模型目录和现有适配器导出“服务商/连接/模型/能力/当前请求路径”清单；覆盖所有当前已注册或已有适配代码的模型。
2. 采集证据：逐模型记录官方文档 URL、访问日期、请求体示例与字段表；缺少官方资料的条目进入 `unverified`，不补猜。
3. 定义合同：先为证据完整的模型添加版本化 `OfficialRequestContract` 与请求体快照测试，再移除该模型对泛化视频参数模式的依赖。
4. 建立路由映射：分别为官方服务商、UniCompAPI 和每个 OpenAI 兼容连接记录传输模式与证据。只有精确的“连接/端点/模型”映射可使用 `official_passthrough`。
5. 接入 UI：动态字段读取合同，显示必填、枚举和约束；前端字段级校验与适配器请求体校验使用同一合同定义。
6. 分批放量：先迁移证据完整且已有适配器测试的模型，再处理其余模型；每批均保留旧中转合同回退，不做全量名称匹配切换。

## Seedance 核对项

`doubao-seedance-2-0-fast-260128` 不可因当前泛化模式没有必填标记，就被认定为“没有必填项”。实施时应以其对应官方版本的请求体文档为准，逐项记录模型字段、输入图片条件、时长、分辨率、比例、提示词及其他约束；文档未声明的字段不展示为必填。

该模型只有在 UniCompAPI 或某个中转连接具备该精确端点与字段兼容证据时，才使用 Seedance 官方请求体。否则维持中转站自身合同或 `unverified`，不得用模型名跨服务商强行复用序列化器。

## 验收标准

- 每个 `official_passthrough` 映射有可访问的证据记录、请求体快照测试和适配器测试。
- 每个已知枚举在 UI 中以有限选项呈现；不存在“文本输入后由服务端试错”的官方枚举字段。
- 每个必填字段在空值、格式错误和非法枚举时均在前端阻止提交，并在适配器层再次拒绝。
- `gateway_contract`、`unverified` 和 `unsupported` 不会发送官方扩展字段；新增 OpenAI 兼容连接默认不会继承同名模型的官方请求体。
- 映射表覆盖当前已注册/已有适配代码的模型，未覆盖项在清单中明确标注原因。
- Windows 回归包括文生视频、图生视频、文生图和专业生图候选加载、模型切换、参数编辑和提交前校验；macOS 继续维持延期目标，不声明实机验收。

## 非目标与风险

本方案不启动阶段 10，不涉及安装包、签名、公证、生产更新、生产媒体组件分发或 macOS 实机支持。不会发送真实服务商请求、读取真实凭证或消耗预算来作为本方案文档的验收依据。

主要风险是中转站“兼容”声明粒度不足。处理原则是宁可保持中转站独立合同或不提供可提交候选，也不把未经验证的官方字段发送到未知网关。
