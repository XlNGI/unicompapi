# 文本流增量持久化批处理实施计划

## 一、阶段与依据

当前阶段仍为阶段 9 已收口，阶段 10 未启动。本计划属于已收口范围内的文本流性能缺陷修复，不新增一级页面、不修改服务商协议、不进入发布准入。

权威依据：

1. 项目负责人批准的“流式 UI 实时显示、增量有界批量持久化、终态强制刷新”优化方向；
2. `AGENTS.md` 与 `PLANS.md`；
3. `docs/active/阶段9-UI与多服务商功能路由最终方案.md` 的运行态短期流式片段与权威持久化事实边界；
4. `docs/active/多服务商功能路由-M2-文本流式合同记录.md` 的顺序、重放、背压、中断和恢复合同；
5. `docs/active/文本模型流式超时统一化验收记录.md` 的公共文本流运行策略。

## 二、问题与目标

当前每个 `content_delta` 或 `reasoning_delta` 都同步执行：读取 execution、读取全部事件、追加单个事件、原子重写项目 JSON 与备份。适配器等待该过程完成后才读取下一上游分片。细粒度 SSE 在一次回答中产生数百至上千事件时，本地磁盘延迟会反向阻塞网络读取。

目标：

- 上游分片读取不再等待每个两三个字符单独落盘；
- 相邻同类型增量按有界时间和大小合并为持久化事件；
- 持久化事件继续保持严格连续 sequence、可重放和项目隔离；
- 完成、失败、取消、中断和应用退出前强制刷新；
- 存储变慢或失败时有明确内存上限并恢复背压，不无限积压；
- DeepSeek、NewAPI、UniCompAPI 和其他 OpenAI 兼容文本模型统一生效；
- 不影响图片、视频、非流式提示词增强和其他服务商操作。

## 三、固定边界

默认策略：

- 批次时间窗口：120ms；
- 单批累计阈值：8KB UTF-8 字节；
- 待持久化内存上限：256KB UTF-8 字节；
- 相邻 `content_delta` 合并，相邻 `reasoning_delta` 合并；
- 类型发生切换时保留原始先后顺序，不跨类型重排；
- 达到内存上限时暂停上游消费并等待持久化追上；
- 终态操作必须等待所有已接受增量完成持久化；
- UI 只发布已经持久化的批次，继续支持按 sequence 重放；
- 后台批次写入失败必须在当前执行内传播，不能静默丢弃或标记完成。

本计划不承诺崩溃时保存尚未达到刷新条件的内存片段。默认最大未落盘时间窗口约为 120ms；已持久化批次和终态事实继续使用原子 JSON 与备份保护。

## 四、实现方案

在服务商适配器与 `ConversationResponseExecutionLifecycle` 之间的共享 linked lifecycle 中建立每 execution 独立的增量批处理状态：

- pending segments：保存有序、相邻同类型合并后的增量；
- pending bytes：使用 UTF-8 字节数计算内存占用；
- flush timer：首次进入空批次时启动一次 120ms 定时刷新；
- serialized tail：复用 execution 队列保证批次严格顺序落盘；
- failure state：后台刷新失败后拒绝后续追加和终态成功；
- terminal drain：完成、失败、取消和中断前清除定时器并等待队列排空。

对话正文投影继续使用现有 120ms 合并逻辑。执行事件批次落盘后再发布受控流事件，因此 renderer 不需要新增 DTO、IPC 或迁移逻辑。

## 五、实施步骤

### 步骤 1｜批处理核心

- 在 `conversation-text-submission.ts` 的共享 linked lifecycle 中加入 execution 级增量状态；
- 合并相邻同类型增量；
- 实现定时、大小阈值、内存上限和终态 drain；
- 保留现有 execution queue、projection queue 和错误传播。

### 步骤 2｜合同测试

- 连续小分片显著减少 execution 事件数量；
- content/reasoning 交错顺序保持；
- 定时窗口到达后自动持久化；
- 大小阈值触发立即持久化；
- 内存上限触发有界背压；
- complete/fail/cancel/interruption 前强制刷新；
- 后台写入失败不能静默完成；
- DeepSeek 与 NewAPI/UniCompAPI 流式回归通过；
- renderer 按 sequence 重放和部分内容恢复不回归。

### 步骤 3｜完整验收

- 聚焦 Node/Vitest 测试；
- `pnpm typecheck`；
- `pnpm lint`；
- `pnpm build`；
- `pnpm test`；
- 平台审计、交接包校验和 `git diff --check`。

## 六、停止条件与回滚

出现以下任一情况时不得宣称完成：

- 批次导致事件乱序、sequence 不连续或重放缺失；
- 终态先于增量落盘；
- 存储失败仍被标记为完成；
- 内存队列无上限；
- 修改图片、视频或非流式调用语义；
- 完整门禁存在失败或跳过。

回滚边界为 linked lifecycle 的增量批处理接线；Conversation、ConversationResponseExecution、IPC DTO、仓储 Schema 和服务商协议均不迁移，能够恢复为逐分片追加而不需要数据迁移。
