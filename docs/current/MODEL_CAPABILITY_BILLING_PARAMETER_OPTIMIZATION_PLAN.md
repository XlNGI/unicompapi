保留刚恢复的模型过滤/协议和原工作台布局，只修正生图页的输入提示、候选读取状态与重试。快速生图和专业生图已共用 `ImageFeatureSubmissionPanel`，在此统一实现；复用视频页 `uc-image-quick__preflight` 的黄色样式、位置和语义，不复制视频整套提交流程，不增加新的模型能力推断、供应商适配或注册表迁移。

### 执行步骤、风险与验收

1. 固化三种不同结果：本地缺输入、查询异常、成功空列表。用当前目录内存副本和最小合成夹具验证模式归属；全程不调用服务商、不改用户注册表。先证明现有界面误报，再实施。
2. 在共享生图提交区统一预检和读取状态，复用黄色样式，增加受控重试及已存在的服务商导航；若现有错误码不足以给具体原因，最小补充类型化错误映射，不解析错误字符串猜状态。不改模型入选规则。
3. 回归快速文生图、专业文生图/图生图：空白进入、仅提示词、仅图片、两项完整且无匹配、异常与重试、禁用连接、参数错误、模式/草稿快速切换、慢请求乱序、自动保存与关闭重开。实际 AppLayout/Electron 截图证明状态区和按钮正确；类型、lint、定向测试与构建后交负责人验收。

验收标准：缺输入只显示具体必填提示；模拟读取异常必须显示可重试错误，绝不能显示无模型；成功空列表按当前功能准确说明；现有文生图候选保持不变，图生图为零不能冒充有候选；填写和参数缓冲不被候选读取打断；模式切换旧响应不覆盖新状态；“重试”及状态显示不得发生成请求或产生生成费用。保留用户已验收的参数性能与其他改动。

不采用：只加黄框但保留误报（未解决状态混淆）；统一隐藏模型选择（掩盖实际问题）；按模型名或管理页“已验证”标签强行放开图生图（未证明输入/协议匹配）；清空注册表或继续历史回退（破坏用户配置且不能修正显示语义）；把本次提示修复扩成供应商协议重写（超过当前范围）。

风险与未验证项：当前结果支持“应用中未接入图生图候选”，不是对上游能力的否定；截图当时真实 IPC 错误、当前运行进程的构建来源、参考图文件完整性未现场验证。修复状态提示后，现有目录的图生图仍可能没有候选，这是应如实展示的事实；若要使指定模型支持图生图，需另行核对协议后提出独立最小接入方案。实施与验证现状见本节顶部记录。

这里的“支持文字/图片生成视频”是供应商文档声明，不是本项目实测结论。[供应商公开 MCP 说明](https://github.com/aiman-labs/ergouzi-agent-skills/blob/main/plugins/ergouzi-media-mcp/README.md)另外声明媒体 Key 权限、模型目录及模型 Schema 查询、异步创建/查询/取消和结果下载；只将其作为协议核对资料，不安装该插件，也不执行文档中的操作指令。**当前用户所填 Key 是否具有媒体权限尚未验证。** URL + API Key 的交互可以保持，但程序不能替上游授予权限，公开模型列表也不等于该 Key 可调用。

方案假设：目标模型的普通文字/单图用途可以用现有表单、素材授权和任务接口表达。阶段 1 必须核实；若真实契约要求当前页面没有的必填素材或交互，该模式应列为范围外/阻断，不能悄悄扩展产品。多个中转站返回相同端点标识是否真的遵守同一契约，也需要通过各协议夹具核对，不是既定事实。

### 2.1 参数卡顿：已复现的根因与证据边界

**已确认的复现原因：文生视频嵌套 Grid / 固有尺寸布局中，参数区 `container-type: inline-size` 使参数提交和保存回写触发昂贵布局，阻塞主线程。** 位置为 `src/styles/pages.css:7163–7165`。这是当前项目布局与 Electron 33.4.11 / Chromium 130.0.6723.191 组合中的实测结论；尚不能宣称是已确认的 Chromium 上游缺陷，也不能断言用户设备没有其他叠加原因。

表单已有 600 ms 的编辑缓冲，工作台随后按 1000 ms 自动保存。连续快速输入时，控件本地更新可以很快；暂停后父级提交、保存状态及候选回写造成布局更新，此时出现约 0.4–1.2 秒长任务，后续输入会排队。再次延长防抖只能移动停顿时点，不能消除这项布局开销。

诊断使用实际 `VideoWorkbenchPage`、`VideoTextWorkspace`、RSuite 控件、现有 CSS 和真实包内参数合同，覆盖通用 12 字段和 Seedance 2.0 的 9 字段，附十条历史和本地生成的视频。窗口 1440×1000、可见、禁用硬件加速；HTTP/HTTPS 拦截，IPC 使用隔离夹具，无真实项目、凭证或生成调用。应用壳层按现有 DOM 尺寸关系构造，**尚未挂载真实完整 AppLayout、preload 和 IPC**，因此诊断不能替代完整应用验收。

| 相同数字编辑操作下的隔离实验 | 最长主线程长任务 | 观察窗口累计 Layout 耗时 | 结论 |
|---|---:|---:|---|
| 壳层布局 + 原参数容器样式 | 755 ms，13 次长任务 | 6781.7 ms | 复现明显停顿 |
| 仅文生视频参数容器改为 `container-type: normal` | 无 ≥50 ms 长任务 | 41.8 ms | 保留状态提交与保存仍消除该瓶颈 |
| 恢复原容器样式 | 1145 ms | 4566.7 ms | 停顿复现，支持因果判断 |
| 通用 12 字段复核：原样式 → 去除该容器 | 1167 ms → 无 ≥50 ms 长任务 | 4588.5 → 35.5 ms | 非单一型号特例 |
| Seedance 9 字段复核：原样式 → 去除该容器 | 1124 ms → 无 ≥50 ms 长任务 | 5064.9 → 27.4 ms | 第二套实际合同重复得到同方向结果 |

这些是短场景的根因实验，不是最终性能压测。第一组原样式与去容器场景各有 4 次保存、4 次候选查询，工作台各渲染 8 次，去容器后仍无长任务；因此不能把“消除全部 React 渲染/IPC”当作修复此瓶颈的必要条件。仅设显式宽度、固有尺寸提示、改 Grid 行、改 details 显示或把容器移到父节点，实验仍有长任务，不能作为已验证修复。

证据产物（本地忽略目录，可复查，非发布内容）：[诊断脚本](../../outputs/text-video-parameter-audit/diagnose.cjs)、[移除与恢复对照](../../outputs/text-video-parameter-audit/app-layout-scenarios.json)、[两套合同复核](../../outputs/text-video-parameter-audit/confirm-scenarios.json)、[未奏效的局部样式实验](../../outputs/text-video-parameter-audit/minimal-style-scenarios.json)、[场景总报告](../../outputs/text-video-parameter-audit/report.json)。该目录同时保留 CPU profile 和截图；渲染器错误为 0。隐藏窗口和初始化时序失败的早期尝试不计入本表。

**测量纠偏：** 从渲染器 input 回调开始计时会遗漏事件在主线程的排队时间；有的原样式场景输入回调到绘制机会仍仅约 11 ms，却存在 755 ms 长任务，另一次样本达到 1718.6 ms。后续验收必须包含连续输入、停顿提交、自动保存与候选更新的整个时间窗口，同时记录输入派发至处理、至绘制机会和长任务，不能用单个低 p95 证明不卡顿。累计 Layout 耗时也不等于单次按键延迟。

### 2.2 参数正确性与上一轮为何漏检

- **另一个已复现缺陷：多字段一起刷新会覆盖前面的值。** 探针在同一轮先写 `frames=25`、再写 `seed=42`，不触发失焦，立即点击生成；保存结果为 `{seed:42, resolution:"720p"}`，`frames` 丢失，见总报告 `seedance9-two-pending-flush`。这是程序构造的多缓冲字段场景，证明提交合并错误，不声称每一次日常逐项填写都会触发。
- 根因在 `VideoFeatureSubmissionPanel.tsx:386–403`：每次读取 `draftRef.current`，却从尚未同步的 `featureSelectionRef.current` 合并参数；第一次回调只更新 draftRef，第二次仍用旧 selection 覆盖它。应让整个同步刷新基于一份最新完整快照，不能仅凭代码注释或存在 ref 判定安全。
- `DynamicParameterForm` 尚未进入工作台的 `registerPendingEditor` 统一刷新链路；创建草稿、切页和关闭时未提交参数是否丢失，当前是**静态风险，未运行时证实**。实施先补行为断言，确认失败再补必要接线，不预先宣称丢值已复现。
- 原 `verify-video-workbench-electron.cjs` 主要测图生视频提示词，参数夹具只有一个数字；独立参数探针没有整个工作台尺寸链。前次 `986c3df` 解决图生视频提示词即时耦合，不能覆盖这次文生视频参数布局和多字段刷新。
- 本轮重跑 `node --test tests/ui/parameter-input-decoupling.test.mjs` 为 **5 通过 / 1 失败**：一项源码正则只接受 LF，在 CRLF 文件上失败；多字段相关源码断言却通过，仍挡不住上述行为丢值。后续用运行时数据断言验证，不把通过的源码匹配数当成体验保证。
- 普通编辑确有全字段重渲染，文生视频提示词也仍使用普通受控 Input；前者可能放大成本，后者是独立输入路径。二者均不足以推翻上述布局对照，也不据此扩大为全表单状态管理重构。

### 3. 用户交互与界面效果

- **添加与同步：** 保留 URL、API Key 和现有同步按钮。一次同步内部完成模型列表和必要的元数据补全，不增加用户步骤。按现有规则保留旧模型开关；新模型继续默认停用，用户自行启用。
- **启用：** 开关只表示允许使用该模型。可从已有可信信息构建所需 profile，但不得因为开关打开而发明能力，不自动调用生成接口进行探测。
- **管理页：** 复用现有行、状态标签和详情区域。正常行显示具体功能，例如“文生图”“文生视频 / 图生视频”；异常只显示一条原因，如“模型信息待补全”“当前版本暂不支持此接口”“当前工作台不支持此用途”。不增加面向用户的 adapter、Schema、协议版本等技术字段，不将内部 profile 的 verified 直接表述为“真实调用已验证”。

- **素材尚未填写：** 图生视频模型的归属不依赖用户是否已经上传图片；允许先选模型，按现有表单在点击生成时提示缺少图片。需要源视频或专用音频流程的模型不能混入普通文生/图生视频。

- **参数录入：** 保留原位置、控件、默认值、提示和校验；文本/数字即输即显，下拉立即响应，停顿等待自动保存时也不能冻结。生成、新草稿、切页和正常关闭前提交末尾有效值；无效数字阻止生成且保留编辑内容。修复后的可见变化应是更顺畅、值完整，而不是换一套表单。

### 4. 最小实现契约

**A. 补齐一次同步中的信息，而非建设新的能力管理系统。**

- 当前连接的模型目录决定参与合并的模型集合；元数据只按精确模型 ID 补充该集合，公开模型广场中的其他模型不得自动导入或代表 API Key 具备调用权限。
- 先解析目录中已知语义的端点/能力字段；不足时，NewAPI/OpenAI Compatible 连接在同一次同步中补充一次同源 `/api/pricing` 请求。按协议识别，不按二狗子或 UniCompAPI 域名硬编码规则；其他已接入供应商保留其现有发现适配器。对目标异步模型，仅在先行核实其发现契约后接入同源、受控的模型详情读取；不把 `api_schema_endpoints` 的标识当成可直接访问的 URL。
- 复用受控传输、凭证与来源限制；上述 pricing 补充请求最多一次，额外等待预算 3 秒，响应上限复用现有 8 MiB。不枚举猜测 URL，不跟随跨源凭证跳转，不因接口 401/403/404/429 自动重试或要求管理密钥。
- 必要的模型详情只通过已经注册、文档已核实的发现协议读取；当前没有适配的详情协议保持“未接入”。详情查询的端点、数量上限、总超时和缓存失效条件在阶段 1 核实后固化，不能形成逐型号无界网络请求。本次不实现任意网站爬取、远端 JSON Schema 自动执行或万能协议编辑器。
- 元数据暂时失败属于“本次未更新”，不能伪装成空能力声明。连接配置及凭证版本未变时保留原可信能力，标记刷新失败；首次发现的未知模型仍待补全。URL/凭证版本变化后，旧观测不能自动迁移到新配置。

**B. 一处连接内功能判定，复用现有能力与 profile。**

- `ProviderCatalogEntryV1` 增加可选的规范化声明（已知端点、已明确的 ProductFeature、来源类型、版本/内容指纹、获取时间）；旧 ID-only 返回仍合法，不再丢掉可用信息。
- 将声明通过现有 registry 事务关联到 `modelId`，同时检查 `connectionId` 及配置版本。已有 ModelCapabilityEvidence / ModelFeatureProfile 继续作为持久化载体；必要的来源字段增量扩展，不建平行数据库或新管理 IPC。
- 统一判定返回目标功能的“支持 / 未知 / 不支持 / 信息冲突”与执行契约是否就绪。管理 DTO 增加派生的功能标签及原因码；候选与提交复用该判定。
- 输入模态不等于输出能力：能看图不是能生图，支持视频理解不是视频生成。聊天端点、图片生成端点、图片编辑端点分别解析；`async-model` 仅为协议类别；视频具体模式需要逐模型声明、匹配的已核实参数契约或现有精确定义，不能自动扩展为文生+图生视频。
- 现有官方精确定义保留为已知模型契约来源，作用域只限所属服务商包与连接。陌生型号不再因为未命中固定名单而被重复否决；但名单缺失也不能自动获得不存在的参数契约。普通新型号使用已有且语义匹配的通用协议无需新增型号 if/else。
- 同来源只使用最新未被替代记录；显式撤销使对应旧授权失效，缺失字段不等于撤销。跨来源明确冲突不取并集，标记待确认；有能力但协议/必需字段无法匹配时标记当前版本未支持。网络错误不改成“模型不支持”。
- 修正通用图片/视频合成 profile 及其再生成路径。已明确仅媒体用途的模型不再因通用聊天默认 profile 出现在对话候选；保留正常聊天模型和官方既有接入，用正例回归保障，不做无关聊天重构。

**C. 历史兼容与查询边界。**

- 旧合成证据不再授权，旧记录保留且不改写。合法新证据按同一模型/能力/来源的最大版本递增；只有语义变更才写入，重复同步不重复追加。
- 同步/启用在明确事务中建立合法 profile；候选查询不再通过路由器制造事实或写注册表。旧数据由兼容解析和统一判定处理，需要补资料时提示同步，不要求用户删除重建连接。
- 提交准备及提交前复核沿用现有候选重解析和路由指纹机制，能力、连接或配置变化使旧 token 失效。参数缺失在原表单校验；无效能力在外发前拦截，不能等待生成失败才发现归类错误。
- 同步原子提交并检查连接版本；慢的旧请求不得覆盖新 URL/Key 下的数据。单条不认识的元数据不令整个目录失败，保留可解析模型和该条诊断。

**D. 补齐现有用途的必要执行接入。**

- 在写实现前核对 Seedance 2.5 和普通 e-video 的真实协议材料：鉴权与媒体权限、能力/模式描述、必填输入及互斥条件、创建/查询/取消、结果结构。生成请求不作为能力发现手段。
- Seedance 2.5 优先复用已有视频适配器；仅在请求契约吻合时绑定，差异按协议字段修正，不以型号名放行。普通 e-video 的异步协议通过项目已有适配器接口接入；复用任务生命周期、受控下载和本地作品校验，不新建任务系统或费用系统。
- 新适配只覆盖现有文字/单图用途。需要新素材类型或新操作流程的模式保持不支持，不把普通提示词偷偷改成口播脚本，也不忽略源视频必填条件。
- 核心判定依据规范化能力和执行契约，不按站点域名分支。协议适配必须有明确文档；不同站点只有在确实实现同一契约时才能复用，不能因都叫 `async-model` 就视为兼容。
- 契约缺失时停止该模型的放行，写明缺少哪项协议事实；通用筛选修复可独立验证，但目标模型仍列未完成，不把总任务标记已修复。工程侧负责查明协议，不能将其变成用户逐模型填配置的负担。

模型预计变更边界：`newapi-chat-adapter.ts` / `newapi-runtime.ts` 承接受控发现；`provider-management-framework.ts`、现有 registry/domain 契约增量保存必要来源；现有图片/视频路由及 `provider-registry-feature-candidates.ts` 统一筛选；管理页仅接现有行状态；仅在上述契约核实后补充必要协议适配。复用现有参数 Schema、候选与提交复核服务，不建设通用插件平台，不改变工作台视觉结构。准确文件清单随阶段 1 的契约核对确定，不能为整理代码扩大范围。

**E. 参数区只修已定位的布局和数据边界。**

- 在文生视频作用域移除造成瓶颈的参数容器尺寸查询依赖，并以现有 Grid 的内在自适应规则保留窄屏单列、足宽双列；不全局删除容器查询，不以扩大防抖或升级 Electron 代替局部修复。当前仅“关闭该容器”的窄栏因果实验通过，宽栏响应式替代仍须实施时验证，不能直接把诊断注入当成成品补丁。
- 检查 `@container (min-width:620px)` 在取消最近容器后是否误匹配更外层容器；须将受影响的参数列数规则一起局部约束，避免窄栏因外层很宽而变双列。保留字段顺序、对象参数跨行、标签与控件对齐、弹层可见性和滚动行为；在 620 px 前后及实际侧栏宽度截图比对。
- `VideoFeatureSubmissionPanel` 的模型切换、字段提交与生成前刷新统一从最新草稿快照合并；一次刷新多个字段必须全部保留，后一次无意覆盖前一次即为失败。继续复用当前 600 ms 编辑缓冲、校验和保存协调器。
- 将参数 pending edits 纳入现有工作台刷新边界的行为回归；若新建/切页/关闭测试证实缺失，再连接既有注册与清理顺序，禁止生成第二套自动保存器。无效值不得变成旧值悄悄提交；保存失败不能丢掉本地编辑内容。

### 2.1 问题一：视频页出现生图模型

已确认根因不是视频页单纯漏过滤，而是通用 NewAPI/OpenAI Compatible 路由在平台层伪造了模型能力。

调用链：

```text
VideoFeatureSubmissionPanel
  -> preload videoFeatures.listCandidates
  -> VideoFeatureController.listCandidates
  -> ProviderFeatureCandidateService.listFeatureCandidates
  -> RegistryFeatureCandidateSource.list
  -> routeOpenAiCompatibleVideoProfilesForEnabledModels
  -> 持久化 video profile
  -> ModelSelect
```

证据：

- `src/platform/providers/newapi/openai-compatible-video-routing.ts` 对普通 `provider-package-newapi` 不检查逐模型能力声明；连接模板存在 `newapi.video` 适配器时，就为启用模型创建 `text_to_video` 和 `image_to_video` profile。
- `src/platform/providers/newapi/newapi-contracts.ts` 的通用模板同时注册 chat、image、video 适配器。适配器只证明连接存在调用通道，不证明连接下每个模型支持视频。
- `src/platform/providers/provider-registry-feature-candidates.ts` 在候选查询时再次执行路由并持久化结果；候选层按已经生成的 `productFeature` 筛选，无法识别最初伪造的能力。
- `src/platform/providers/provider-feature-candidates.ts` 只校验 profile、route、参数 Schema 的内部一致性；伪造 profile 的三者可以自洽，因此不会被拒绝。
- `src/pages/creation/video/VideoFeatureSubmissionPanel.tsx` 和 `src/components/ModelSelect.tsx` 直接展示返回候选。错误 profile 的 `available` 为真，所以会进入可用分组。
- 本机真实注册表中，`gpt-image-2.5`、`gpt-image-2-auto`、`ergouzi/e-image` 等 `mediaKind=unknown` 模型同时具有图像和视频 profile，证明错误状态已被持久化。
- 现有 `tests/platform/openai-compatible-video-routing.test.ts` 的 8/8 通过并不能证明正确性；其中“普通 OpenAI Compatible 同名模型自动获得视频能力”的测试语义正好固化了缺陷。

结论：普通中转站只有在具体模型存在可信能力证据时才能进入视频候选。不能用模型名称关键词过滤，也不能只在 UI 隐藏。

已确认这不是“所有其他中转站都不能计费”的事实。当前代码只对支持 NewAPI 计费协议的连接启用站点日志/价格对账；通用 OpenAI Compatible 若无同等协议，则只能使用官方价格规则或回退到未估算。

- route：`route-47824ee9-b030-4239-abca-83de493e71bb`，连接 `weq`，模型 `gpt-image-2.5`，创建时间 `2026-09-17T03:34:46.257Z`。

### 2.3 问题三：填写模型参数卡顿

已确认当前输入链路存在同步耦合：

```text
控件 onChange
  -> changeParameter
  -> onDraftChange
  -> 替换整个工作区 draft
  -> setDirty
  -> autosave.queue
  -> 页面/参数区重渲染
  -> 参数校验和候选相关 effect 重新评估
```

证据：

- `src/components/DynamicParameterForm.tsx` 的普通字符串和数字控件每次按键都调用 `onChange`；数组和 JSON 控件虽然有局部 `text`，解析成功时仍立即提交父级。
- `src/pages/creation/video/VideoFeatureSubmissionPanel.tsx` 的 `changeParameter` 复制整个 `parameterValues` 并通过 `onDraftChange` 替换工作区草稿。
- `src/pages/creation/video/VideoWorkbenchPage.tsx` 随后更新 dirty 状态并排队最新快照自动保存。1 秒 debounce 只减少磁盘写入，不能消除按键期间的 React 状态更新和重渲染。
- 当前测试验证了候选读取期间的状态保护，但没有输入延迟、渲染次数或 IPC 频率基线。

尚未验证：需要真实 Electron 性能记录区分工作区重渲染、参数校验、候选 effect 和 IPC/保存回写的耗时占比。静态调用链已足以确定耦合存在，但不能仅凭静态代码断言唯一的 CPU 热点。

结论：输入控件维护本地编辑缓冲；停止输入、失焦或明确提交时才向父级提交稳定值；父级继续使用现有最新快照协调器；参数编辑期间不刷新候选；提交前保留完整校验。

## 4. 唯一推荐方案

### 4.1 能力真源和候选门禁

在平台路由层建立“连接适配器能力”和“具体模型能力”两级事实：

1. 普通 OpenAI Compatible 连接的 video adapter 只允许发起视频协议调用，不自动给全部模型挂载视频 profile。
2. 只有逐模型能力声明、用户对具体模型的显式确认并版本化保存、或可信包级精确模型映射，才能生成对应视频 profile。
3. 未知能力模型从视频候选中排除，不放入“暂不可用”分组，避免用户误选；管理页可另行显示“未确认能力”，但不属于本次视频提交候选。
4. 候选服务增加 capability evidence、adapter route、productFeature、parameter schema、result/usage schema 一致性门禁；门禁放在平台层，UI 只消费结果。
5. 对已持久化的错误 profile 使用版本化迁移或查询时失效：删除/改写前先备份并提供回滚；不能直接改用户 registry。迁移后旧 profile 必须带失效原因和迁移版本，避免下次候选查询重新生成。
6. 重写当前两个错误语义测试，补充 image-only/unknown model 的视频候选回归测试；保留 UniCompAPI 精确映射和显式能力证据的正例。

### 4.2 中转站计费关联、估算和诊断

保持现有 NewAPI 读模型作为协议适配器，扩展其事实表达，不复制一套独立计费真相：

1. 成功响应中的 allowlisted request ID 统一写入 usage observation；若上游没有响应头 ID，要记录 `request_id_unavailable` 诊断状态，而不是静默丢失。
2. 账单 reconciliation 区分 `logs_unavailable_404`、`logs_rate_limited`、`logs_transport_error`、`request_id_missing`、`usage_not_reported`、`pricing_model_missing`、`pricing_invalid`、`currency_unconvertible` 等 bounded reason code。
3. 任务中心显示金额状态和短原因：实际账单、站点预估、官方价格预估、等待对账、无法估算（缺什么）。原始 URL、响应体、凭证和内部错误文本不展示。
4. 对有 NewAPI `/api/log/token`、`/api/status`、`/api/pricing` 协议的中转站，优先请求日志对账；日志无法关联时才使用价格快照和已验证用量进行预估。
5. 对仅提供 OpenAI Compatible 生成接口、没有账单协议的站点，不虚构实际账单；若用户显式配置并确认官方价格规则，显示“官方价格预估”，否则显示可解释的未估算。
6. 价格键必须使用 route 的 `providerModelKey`，并支持经验证的站点别名映射；禁止按模型名称猜价格或写死价格。
7. `/api/pricing` 的精确键、账单日志关联和响应 ID提取先用脱敏 fixture 测试；不以 HTTP 200 作为计费成功证据。

### 4.3 参数输入性能

1. 在 `DynamicParameterForm` 内按字段维护编辑缓冲：文本、数字中间态、数组和 JSON 无效文本都先留在控件本地。
2. onChange 只更新本地输入和轻量本地错误；失焦、回车/明确提交或提交前统一把稳定值发送给父级。
3. 父级只在稳定值变化时替换 draft；参数编辑期间不重新调用 `listCandidates`，不重建不相关工作区节点。
4. 提交前执行完整 schema 校验，阻止无效中间态进入 provider dispatch；取消、切换模型和切换页面时按现有草稿语义 flush 或回滚。
5. 保留现有 autosave 最新快照和冲突保护，不通过无限延长 debounce 掩盖同步渲染问题。
6. 增加开发期性能诊断（输入事件到可见文本更新时间、父级提交次数、候选请求次数、autosave IPC 次数、参数区 render 次数），日志只记录计数和耗时，不记录提示词、凭证或完整参数内容。

## 5. 拒绝的替代方案

| 替代方案 | 拒绝原因 |
|---|---|
| 只在视频页按模型名包含 `image`/`video` 过滤 | 名称不是能力证据，会误伤自定义模型，也无法处理旧 profile 和其他入口。 |
| 只把错误模型在 UI 中隐藏 | 平台仍会持久化错误 route，其他入口和提交链路仍可能使用，根因未修复。 |
| 看到中转站有 video adapter 就默认所有模型支持视频 | 正是当前缺陷的来源，适配器能力与模型能力是两个事实层。 |
| 所有中转站统一套用 NewAPI 账单接口 | 协议不成立时会制造 404/429 和虚假金额；实际账单、站点预估、官方预估必须区分。 |
| 只延长 autosave debounce | debounce 只影响磁盘写入，不能消除每次按键的受控状态更新和重渲染。 |
| 每次输入都发异步保存/候选刷新 | 会放大 IPC、网络和竞态，无法保证最新值且更容易卡顿。 |
| 直接清空本机 registry 中的错误 profile | 破坏用户数据、不可审计、不可回滚，不符合当前授权边界。 |

### P0：补齐证据和性能基线

范围：测试 fixture、脱敏诊断、开发期性能记录；不改变业务行为。

RED：计费 fixture 缺少 request ID、usage、精确价格键或返回 404/429 时，当前模型无法区分原因；参数性能脚本无法给出按键延迟、render、候选请求和 autosave 次数。

GREEN：能对截图调用重建四类事实；能在 Electron 中记录至少 30 次连续输入的 p50/p95 可见延迟、父级提交次数、候选请求次数和 autosave IPC 次数；所有输出脱敏。

停止条件：无法在不读取凭证的情况下重建现场，或性能采集本身改变交互行为。

### P1：修正模型能力真源和旧 profile 门禁

范围：`openai-compatible-video-routing`、候选服务、能力/route contract、相关测试；不改 UI 样式。

RED：普通未知模型被自动生成视频 profile；已有错误 profile 仍能进入视频候选。

GREEN：普通未知/image-only 模型不生成视频 profile；显式能力证据和可信精确映射仍可生成；旧错误 profile 被查询门禁排除且迁移可回滚；候选内部 contract、平台测试和类型检查通过。

停止条件：无法定义能力证据版本，或迁移会不可逆覆盖用户 registry。

### P2：补齐计费关联和可解释失败状态

范围：NewAPI billing adapter、usage schema/read model、任务中心文案和 contract tests；不调用真实付费接口。

RED：请求 ID缺失、账单 404/429、usage not reported、pricing key missing 都只得到 `unestimated`，且没有 reason code。

GREEN：相同 fixture 能得到实际账单/站点预估/官方预估/等待对账/可解释未估算；金额计算使用精确小数；HTTP 200 但 payload 无效不会计费成功；无协议中转站不会伪造账单。

停止条件：无法建立中转站协议能力声明，或价格来源无法审计。

### P3：解除参数即时输入耦合

范围：`DynamicParameterForm`、视频/图片参数提交边界、性能 contract tests；保持现有 schema 校验和 autosave 语义。

RED：输入一个字符就替换整个工作区 draft，候选/保存计数随每次按键增长，JSON/数组无效中间态无法继续编辑。

GREEN：文本立即可见；稳定提交才更新父级；输入期间候选请求为 0；失焦/提交/切换模型时稳定值正确保存；无效值不会进入 dispatch；性能基线 p95 低于 100ms，且无明显输入冻结。100ms 是本项目验收目标，不是博客或系统普遍保证。

停止条件：flush 与切换模型产生旧值覆盖新值、或性能下降超过基线 20%。

### P4：组合回归、构建和 Electron 验收

范围：全部受影响契约、类型检查、lint、生产构建、`git diff --check` 和真实 Electron 手工流程。

自动化 GREEN：相关 Vitest/Node UI contracts、typecheck、lint、production build、diff check 全部通过；无 secret/token 进入 diff、日志或测试 fixture。

Electron GREEN：视频页不显示未确认生图模型；用脱敏 fixture 验证计费状态和原因文案；连续输入参数无卡死，失焦/提交后重开仍是最新值；候选不因输入字符刷新。

## 7. 风险、回滚和停止条件

- 能力收紧可能使某些中转站暂时没有视频候选；这是未知能力的诚实结果，只有拿到逐模型证据后恢复。
- 旧 profile 迁移若只在查询时失效，注册表仍保留历史数据；若增加版本化迁移，必须先备份、记录迁移版本并支持反向恢复。
- 计费接口受限或协议不兼容时，系统只能展示“无法估算/等待对账”；不得用猜测金额替代事实。
- 本地性能目标受机器、开发构建和 Electron 负载影响；必须记录环境、构建模式和样本数。
- 每阶段可独立回滚到阶段前提交；禁止直接修改用户 AppData 数据作为修复手段。
- 若同一假设连续三次修复失败，停止局部打补丁，重新检查所有者、事实真源和契约。

## 8. Git、隐私和授权

从 `develop` 创建 `feature/*` 分支实施；每阶段一个可回溯提交，保留本地和远程分支。方案阶段不创建分支、不提交源码。

测试 fixture 只允许使用脱敏 ID、状态、计数和金额；禁止 API Key、Token、完整响应体、提示词、绝对用户文件路径进入仓库。外部站点查询仅在负责人明确授权并记录范围、时间、响应状态和费用事实后进行。

## 9. 未验证项清单

1. `weq` 当时 `/api/pricing` 是否包含精确键 `gpt-image-2.5`。
2. `weq` 账单日志是否曾包含与该图像请求相同的上游 request ID；当前调用记录显示 request ID 未进入 usage。
3. 普通中转站是否能提供逐模型视频能力元数据。
4. 参数卡顿在真实 Electron 中的主要耗时分布，以及 P3 改造后的实际 p95。
5. 生产环境中各中转站的账单协议覆盖率和汇率规则。

## 10. 审核结论

当前证据支持上述唯一主线，不能支持“先改 UI 过滤”“所有中转站直接套同一计费协议”或“仅延长 debounce”。不需要推倒重来：现有 provider route、billing read model、autosave 和参数 schema 都可保留，修复集中在能力证据门禁、计费关联/诊断和输入状态边界。

负责人审核通过后，下一步只进入 P0；P0 完成后暂停并提交验证证据，不自动进入 P1。
