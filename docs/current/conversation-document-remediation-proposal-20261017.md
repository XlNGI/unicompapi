# 通用会话与文档能力改进方案（2026-10-17）

状态：方案已形成，尚未进入详细设计或业务实施。本文中的目标行为、工具接线、验收用例均是拟实施要求，不表示当前已经支持或通过。

## 1. 目标与范围

依据[会话与文档审计](conversation-document-audit-20261017.md)的 A01—A09，保留通用会话助手定位，支持围绕资料讨论、分析、制定方案、按需求生成和修改 Word / Excel / PPT。PPT 的专业视觉设计与持续修改是本轮重点。

负责人要求的顺序为“先审计，再做方案，再设计”；本轮只形成方案。范围限于本文、方案验证记录和 PLANS 顶部登记，不改业务源码、现有测试和审计原始证据，不生成 Office 成品。

本轮排除图片素材、搜图和配图能力。保留现有本地 Office/PDF 渲染检查。没有新增业务一级页面、登录、会员、充值或云同步，也不预先绑定模型、服务商或外部视觉审核服务。

目标体验是用户在同一会话中逐步推进工作，系统可靠执行当前意图。讨论、方案、设计和文件生成可根据需求往返，不设置固定问卷、必经三页预览或逐步点击的向导。用户已明确要求执行且范围清楚时，直接在已授权范围内执行；只有必要歧义、范围扩大或既有门禁要求时才追问。

## 2. 会话行为要求

| 用户表达与上下文 | 目标行为 | 文件副作用要求 |
| --- | --- | --- |
| “先审计，再做方案，再设计” | 当前先完成审计，记住后续顺序；不能因提及设计或 PPT 就开始生成 | 不调用 Office 生成或修改工具 |
| 审计完成后说“继续” | 承接当前待办，进入方案；不能把同一句继续解释成所有后续步骤均获执行授权 | 不越过当前阶段生成 Office 文件 |
| “先讨论 PPT，不要直接生成” | 讨论内容与设计方向，保留暂不生成约束 | 不得把生成工具设为 required；Host 拒绝不符合当前要求的写入提议 |
| “先看看大纲”“这个方案再改一下” | 在会话中处理用户指向的内容；不把确认大纲自动扩大成确认生成文件 | 按当前讨论范围处理 |
| “现在按刚才确定的内容生成 PPT” | 复用已确定要求，调用受控生成工具 | 一次任务登记一份对应作品，不重复询问已有信息 |
| “按这个方案生成 Word / Excel” | 与 PPT 一样由会话工具进入既有文档服务，使用对应类型的校验与读回 | 不在后台改成另一种文件，不要求用户切换业务页面 |
| “第二页太散，保留数据重新排版” | 绑定当前作品、版本与物理第二页，实施视觉修改；必要时针对缺失信息追问 | 新版本只改变授权范围，保留原作品 |
| “内容也太多，帮我重新组织” | 根据上下文判断允许的内容与分页调整；保持事实依据和明确的页数约束 | 不能把纯版式授权扩大为任意删改内容 |
| “刚才改过的地方保留，其余页不要动” | 从真实最新版本与已验证修改事实继续 | 非目标范围保持；冲突先核对，不凭旧回复推断已保存 |
| “停止”或结果未知 | 复用现有取消与对账语义 | 停止新副作用；未知结果不自动重发生成 |

这里的阶段是当前会话任务的语义约束，不要求新增一套覆盖 Agent Run / Response / Document Runtime 的独立执行状态机。自然语言判断不能仅依赖“直接、立即、生成”等孤立关键词；明确否定、条件和顺序要求必须在工具准入中生效。

## 3. 推荐改造方向

### S1. 统一“讨论还是执行”的准入语义

复用现有 Agent / Workflow 的语义计划和 Host 准入边界。普通消息、复杂意图及多轮指代由模型结合上下文提出语义建议，明确的本地停止与高置信规则继续由应用处理。Application 校验任务、用户要求、操作、范围、版本和授权事实，模型不能直接创建权限。

将“工具可用”“用户允许本次写入”“必须完成某个已授权交付物”区分开。工具存在不意味着需要强制调用；只有当前用户要求或仍有效的已授权任务能够要求实际写入。否定句不能因为包含正向动词而产生 required 生成。

执行依据绑定当前任务、要求版本、目标作品与范围。用户在同一范围内继续修改不重复走一套确认问卷；变更交付物类型、目标作品或明确要求重新确认时，原执行依据不得静默扩张。通用的“继续 / 可以”应承接具体待办，不能单独授权从讨论跨越到所有文件操作。

关联现状：[原生准备与 required 判定](../../src/platform/documents/conversation-document-tool-session.ts#L282)、[语义计划](../../src/domain/entities/conversation-intent-plan.ts)、[Workflow](../../src/domain/entities/conversation-workflow.ts)。

### S2. 保留有来源、可修订的任务要求

在现有任务与会话事实中保留经过校验的要求摘要，使主题、受众、交付物类型、当前推进范围、风格、内容保留要求和用户排除项可以跨越最近 40 条历史 / 8 条设计 brief 的窗口。每条有效要求应能追溯到用户消息及版本；用户后续修改应覆盖相同范围的旧要求。

模型可建议抽取与合并，Host 负责来源、范围、长度、版本和冲突验证。附件、网页或模型自行总结不能新增执行授权、联网授权或费用权限。删除 / 撤销来源后依原有规则重新核对要求。保持上下文上限和按需引用，不通过无限拼接历史解决遗忘。

当前阶段、已确认事实和仍有效的要求应同时到达普通回答、内容规划、PPT Art Direction 与视觉修订，避免同一任务在不同入口各取一段原始消息。摘要冲突时仅追问冲突部分；与当前任务无关的旧文档要求不得跨作品自动继承。

关联现状：[上下文装配](../../src/application/conversation-context-builder.ts#L52)、[原生设计 brief](../../src/platform/documents/conversation-document-tool-session.ts#L1104)、[任务 Session](../../src/domain/entities/conversation-agent-session.ts)。

### S3. 补齐多类文档的受控业务工具

推荐保留现有 `generate_pptx` 兼容合同，为 Word / Excel 增加相应受控业务生成适配，底层复用现有 DocumentGeneration 服务、编译器和文件生成器。三种类型共享任务所有权、总预算、取消、幂等、Work / File / Hash 校验、正式收据及 Thread 投影，不复制三套 Agent 循环。

已有文档读取与修改按格式能力接线。模型只看到用户可理解的业务参数和受控引用；Host 解析真实文件、绑定版本和范围，不接受模型提供路径、凭证、权限或正式作品登记决定。读取结果必须说明实际读到的结构范围，不能用模型记住的大纲代替当前文件。

| 文档类型 | 本轮目标能力 | 范围边界 |
| --- | --- | --- |
| Word | 原生会话新建、真实结构读回、既有受控章节 / 文字修改 | 使用当前文件执行器支持的操作；不扩大为任意排版软件能力 |
| Excel | 原生会话新建、真实表结构读回、既有受控单元格 / 表内容修改 | 保留未授权单元格、公式与工作表；不新增宏、外部数据连接或任意脚本 |
| PPT | 新建、真实物理页读取、现有对象修改、指定页或全篇视觉修订 | 视觉修订使用真实作品与可信生产计划；范围随用户要求验证 |

必须以单一来源声明实际可用能力；未具备真实读取、修改与验收证据的操作不得对模型宣称支持。旧 IPC 作为兼容入口调用同一业务边界，保留原有读写和显式回滚行为。Word / Excel 原生生成不能再由单独的兼容 IPC 测试替代验收。

关联现状：[规范工具目录](../../src/domain/entities/canonical-tool-contract.ts)、[文档应用服务](../../src/application/document-generation-service.ts)、[现有真实 Office 结构读取与受限修改](../../src/platform/documents/office-document-tool-executor.ts#L121)、[格式生成器](../../src/platform/documents/office-document-generator.ts)。

### S4. 让 PPT 修改操作直接作用于可执行设计

在当前会话中提供基于已有作品的语义视觉修订入口。Host 读取并校验原作品及其生产计划，模型在授权页范围内提出新的构图与样式建议；系统执行同一 Design IR / designTree、Layout IR、渲染、校验和新版本登记链路。

新规划继续由模型根据内容决定构图，系统求解并忠实执行。这里不另建固定版式目录，不把“更专业、太散、重点不突出”简单替换为某个预设模板或单一配色。需要澄清时针对实际问题自然追问；已有足够信息时直接形成有效修改。

针对 A04，旧 visualTreatment 不能直接叠加到新版 designTree。简洁化、流程表达和配色修改需要落到新版可执行结构、palette 或具体样式。兼容旧设计须明确转换边界，不能放宽新解析器来掩盖字段冲突，也不能只改 colorDirection 就宣称页面配色已更新。

修订结果校验至少区分三种情况：

1. **有有效修改**：实际目标页几何 / 样式 / 合法内容发生符合请求的变化，非目标范围保持，候选渲染与文件门禁通过后登记新版本。
2. **已经符合要求**：没有必要修改时说明实际原因，不把 unchanged 异常当成生成失败，不为制造版本而重复登记。
3. **未能落实修改**：用户要求尚未满足而实际页面无变化，或设计不可执行时，返回明确结果；不得把内部意图字段变化当成修改成功。

局部修订不得通过改变全局字段意外影响其他页；全篇改色与指定页改色分别验证。内容、数据、页面 / 元素身份和修改来源保持可追溯。旧作品没有可信设计计划时，只暴露确实能执行的读取和修改能力；基于提取内容重建须符合用户实际请求，并说明保留范围，不能伪称无损重设计。

关联现状：[视觉 revision](../../src/application/presentation-design-revision.ts)、[已登记生产计划读回](../../src/platform/documents/presentation-production-plan-reader.ts)、[Render Plan 编译](../../src/platform/documents/presentation-render-plan-compiler.ts)、[Office IPC 接线](../../electron/ipc/document-generation-ipc.ts#L198)。

### S5. 让内容组织、设计检查和修正共享范围与预算

保留内容快照与引用完整性。纯视觉修改中的内容密度问题应产生可解释的诊断；未经内容调整授权，不得为适配版式自动删事实、改数字或增加页数。用户要求已包含内容重组时，允许在其范围内回到内容规划，之后重新绑定快照和设计，最多执行一次这样的上游回返；再失败则交付明确问题，不无限往返。

区分可执行性错误、格式校验错误、确定性视觉风险与主观风格意见。修正反馈应针对目标页和实际失败原因；错误分类不得泄露内部 Prompt、凭证、路径或原始完整资料。

建议将初次设计后的格式、约束和渲染修正共用现有最多两次模型修正额度。各类修正都消费同一父任务的剩余 deadline、调用步数与预算，不分别重新计数。内容回返也必须占用既有步骤 / 预算，涉及模型修正时占用上述两次总额度，不增加独立循环。超时、取消、额度耗尽或结果未知均停止新操作。

保留负责人已经批准的最多一次本地基础模板兜底，并满足原有适用范围和候选上限。兜底只用于已授权生成，不用于突破讨论限制、修改范围、内容身份、预算或取消状态；UI / 交付说明继续据实际结果区分自主设计与模板兜底。已有作品视觉修订不因失败自动改为整篇模板重做。没有真实外部费用事实时继续保留 unknown，不能把本地调度单位写成金额。

关联现状：[统一预算](../../src/application/execution-budget.ts)、[设计修正](../../src/platform/documents/presentation-design-planning.ts)、[候选与收据](../../src/platform/documents/presentation-design-attempts.ts)、[兜底策略](../../src/platform/documents/presentation-template-fallback.ts)。

### S6. 分别建立“执行正确”和“视觉满意”的证据

技术门禁继续验证真实文件、内容、物理页 / 对象身份、版本、Hash、渲染、边界、局部修改范围、原子发布和唯一作品登记。PPT 视觉修改还要对比实际执行后的目标页结构与样式，拒绝用 IR 意图字段单独证明改动已落实。

确定性视觉信号需要结合内容和图层解释，避免将背景或大包围框面积简单相加视为拥挤。风险提示是否阻止交付，应按问题实际影响分级；已有文件损坏、越界等硬门禁不得放宽，也不能把所有主观 warning 一律升级为失败。

视觉质量单独组织评审，关注阅读顺序、信息层级、重点表达、留白与对齐、原生图表可读性、全篇一致性及变化节奏、修改意见落实情况。等事实材料对比当前基线和改进结果，不靠自动自评分宣称专业。没有完成视觉评审时，状态应明确为未评审；文件技术合格仍按实际事实记录。

真实模型输出的视觉质量需要独立用例验收，使用经授权的模型和预算；本方案不发起任何调用，也不将历史 Mock 或合成构图追认为审美通过。多模态审核是可选扩展，不能以未绑定外部服务为由阻止本地评审或预先绑定供应商。代表页预览可由用户主动要求，不成为每次生成的强制流程。

关联现状：[视觉信号](../../src/platform/documents/presentation-visual-audit.ts)、[当前自主设计证据及限制](../evidence/llm-autonomous-design-20261014/validation.json)。

## 5. 建议实施顺序与交付边界

以下 B1—B5 是本次维护的小批次划分，不对应历史项目阶段。进入实施时从当时最新 develop 建立 feature/* 分支，拆分为可审查的小 PR；保留本地与远程功能分支，不混入当前视频分支的功能交付，不删除已有审计证据或用户改动。

| 批次 | 范围与依赖 | 可独立审查的交付 |
| --- | --- | --- |
| B1：会话准入与要求保留 | 先完成 S1 / S2 | 修复讨论 / 生成误判；要求来源、更新与续接语义；必要的否定、跨轮与无写入回归 |
| B2：PPT 持续修改 | 基于 B1；优先解决当前痛点 | 修复自主树视觉 revision；接通已有作品的原生语义重设计；有效修改 / 无须修改 / 未落实修改的真实结果 |
| B3：Word / Excel 原生接线 | 基于 B1，复用 B2 中通用的作品版本边界 | 三类文档生成和既有受控读写的能力声明、工具适配及真实原生会话验收 |
| B4：内容 / 设计协同与质量检查 | 在 B2 / B3 稳定后做增量 | 有界内容回返、共享修正额度、风险分级与模板兜底结果统计；不引入额外执行器 |
| B5：整体验收 | 依赖前述批次 | 全回归、Windows 原生链路、长会话与恢复矩阵；获授权后真实模型质量样例及独立视觉评审 |

每批均记录实际修改、真实执行的检查、失败项、剩余限制和下一步。任何一批完成不能扩写成整个方案已实现。回滚应复用既有显式入口与版本机制，已登记作品不可因回滚消失；未知副作用仍冻结对账。
