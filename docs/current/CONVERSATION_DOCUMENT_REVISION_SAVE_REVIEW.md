- 20:55 的页码提问及回答均已保存在会话中，20:59 的清空请求与失败状态也已持久化。不存在需要用户先手动保存该任务的前置条件。

- 实际 PPT 共 13 页，验证大纲共 8 个正文节。物理第 7 页为“AI短剧的典型场景与成功案例”；正文第 7 节“数据验证：AI短剧与传统短剧效率对比”位于物理第 10–11 页。此前问答把正文第 7 节当成物理第 7 页，正是前轮发现的成品页读取缺失。

## 根因与业务判断

1. **章节与页面映射失真。** `src/application/document-revision-agent.ts` 的 `revisionTarget()` 对章节目标采用 `sectionIndex + 2` 推算 PPT 页码；`revisionSectionIndex()` 对页面目标采用 `ordinal - 2` 推算大纲节号。它们只适用于封面加每节一页的情况。本例第 7 节被推算为物理第 8 页，但实际第 8 页为“AI短剧制作中的主要挑战与应对方案”。`document-generation-runner.ts` 的 `assertRevisionScope()` 校验页标题与目标章节不一致，拒绝发布新版。该拒绝保护原文件是合理的；错误在于上游范围映射。
2. **失败语义被压平。** `document-generation-application-adapters.ts` 把 `verification_failed` 映射成 `generation_failed`；`ChatPage.tsx` 显示“生成或写入失败，未登记作品”和“未保存文件”。用户无法区分目标未定位、验证失败、实际写盘失败、已登记但对话回写失败。截图中的失败发生在发布/登记之前，不能解释为原 PPT 或聊天未保存。
3. **重试策略丢失可恢复性。** 底层执行明确 `not_retryable`，但上层交付状态归为 `execution_failed` 并开放“重试失败文档”，导致相同目标错误连续重演。任务失败通用文案“尚未全部完成，已交付作品已保留”也没有说明本次单文档修改的新旧版本状态。
4. **保存完成存在多个状态边界。** 当前会话 JSON 采用带 revision 校验的原子写入；文档采用临时生成、验证、发布、File/Work 登记、执行完成、对话挂接与 workflow 结算。自动保存和验证后发布的基本原则合理，但这些步骤跨多个持久化写入，必须按已发生事实呈现状态并支持补写。前轮隔离修复已覆盖部分“Work 已登记而完成状态写入失败”的恢复；本次日志不是这一故障。

## 建议方案与实施顺序

1. **先统一文档定位。** 生成/修订成功时保存与 Work 及文件 Hash 绑定的页面映射：实际演示顺序、slide 标识、章节标识、章节覆盖页与续页。问答和修改复用同一映射，禁止用固定加减法或未经验证的标题匹配替代。旧作品先读取实际 PPT 重建映射，无法唯一对应时先澄清，不能猜。
2. **区分页和章的修改范围。** “第 7 页”只操作物理第 7 页；“第 7 章”操作对应章节全部页面，本例为第 10–11 页。前轮刚讨论页面而新指令改用章节时，在执行前显示文件、版本、标题和实际页范围；存在意图歧义时确认范围，不能默默把章当页。明确清空继续使用受控本地修改，无需再次请求模型正文。
3. **按真实阶段反馈与重试。** 保留 `target_unresolved / revision_scope_violation / verification_failed / write_failed / registration_failed / result_sync_pending` 等可判别原因、执行阶段、是否已发布/登记、可恢复性。此例提示应为“未能定位第 7 章对应的实际页面，本次修改未交付，原 PPT 已保留”，操作应是核对范围/修复映射，而非原样重试。写盘的临时故障才提供保存重试；Work 已登记但状态回写失败只补写状态，禁止重建作品。
4. **明确三个保存对象。** 对话已保存、原作品已保存、本次修改未交付分别展示。成功时自动交付新版本并关联父 Work；原文件不覆盖。失败任务保留诊断和修改意图，取消仅停止本次修改。用户不应承担手动保存聊天/任务才能继续修改的隐藏步骤。

## 验收要求与边界

回归应覆盖本例 13 页/8 节/续页结构，问第 7 页后修改页与章、清空第 7 章的第 10–11 页、其他页内容/Hash 不变、旧版本文件 Hash 不变、错误范围禁止直接重试、重开项目保留对话/失败原因/原 Work。另注入写盘失败、登记失败、登记后状态回写失败，验证不同提示与幂等恢复；真实模型调用保持为 0。

初步评审通过实际记录、同一文件缓冲区 Hash 和真实演示顺序对照源码；初次 .NET 默认共享模式读取被已打开文件的共享限制拒绝，随后以只读且允许共享写入的句柄读取到内存，并确认 Hash 与登记版本相同。这不影响历史失败原因判断，未关闭或改动用户正在打开的文件。实施验收使用独立临时项目和真实生成的 PPTX，不在用户原作品上注入故障。

## 已实施内容

- 统一通过 `presentation.xml` 与 relationships 的演示顺序读取、修订和检查 PPT；封面、隐藏页和空白页均占实际页号。页问答保持单页读取预算，修订最多读取 128 页、累计 64 MiB XML；注册作品读取有文件大小、项目范围、Work/File/execution 关系及同一缓冲区 SHA-256 校验。
- 新增与 Work、文件 Hash、验证大纲绑定的可重建章节页索引；读取时从真实文件重建，缓存不作为授权依据。生成/修订完成后尝试登记派生索引，索引写入失败不改变作品已保存的事实。章节标题重复、不连续或无法唯一对应时拒绝猜测；封面/无章节的空白页不能作为正文局部修订目标。
- PPT 局部修订不再按固定偏移生成目标。确认界面显示文件、版本时间、章/页单位、章节标题及实际页范围；内部保存文件 Hash，确认和执行前复核，Hash 不外露到 Renderer 合同。模型输出与 Renderer 均不能指定可信源 Hash 或文件路径。明确清空仍执行本地受控工具。
- 原件经过验证的同一缓冲区直接交给修改器。逐项比较 PPT 压缩包内容，目标页 XML 外的页面、关系、媒体及样式必须保持一致；新版另存并关联父 Work。页内数字不能仅因等于页码而被当作页脚；页脚按已知形状识别。
- 目标章节的验证正文从实际修改成品回读。修改一页后仍保留同章未改续页的文字，防止下一次修改误认为整章已清空。该正文快照用于文字语义，不声称重建了成品的表格/图表视觉编辑模型；成品原结构由局部补丁保留。
- 分开传递 `revision_scope_violation`、`verification_failed`、`write_failed`、`registration_failed`、`result_sync_pending`。失败提示区分对话已保存、原作品保留、新版未交付、已保存待同步；执行诊断只记安全失败码，不记录底层原始路径或异常内容。
- 范围/校验/内容限制错误归入 `input_required`，新失败任务不提供普通重试，后台亦拒绝直接重放。旧 `generation_failed` 只有底层执行标记可重试才允许恢复；写入、登记及结果同步失败提供相应恢复。首次输入与恢复输入统一归一化，防止默认模板差异改变幂等标识。
- 本地修订助手消息与执行身份持久化绑定；Work 已登记而执行终态或对话挂接失败时复用已验证作品，不再次生成文件。若对话结果同步和 workflow 结算同时中断，重开项目从已持久化状态恢复同步入口；结算异常不能掩盖原失败原因。
