## 1. 本轮决策与产品目标

负责人明确要求改良会话业务逻辑，推翻由本地正则识别用户业务意图的做法。新方案采用 **LLM 理解与规划、Application 校验和调度、Platform 受控执行**。默认自主完成任务，减少追问和人为步骤，并给予 PPT 设计足够自由。

本决策覆盖旧规则中“本地规则处理明确请求，复杂或歧义请求才调用 LLM”的业务路由策略。输入安全、取消、权限、预算、版本、文件和作品登记仍由程序确定性处理。不能把旧正则移到 Application 校验器中，继续以“未命中创建词”“没有主题关键词”等理由否决语义计划。

用户应得到这样的体验：

> 用户：分析这个销售表，做一份给老板看的汇报 PPT，突出问题和下一步建议，样式你决定。
>
> 助手：我先分析销售变化和主要问题，再整理成适合管理层汇报的 PPT。版式我来安排。
>
> 助手进度原位更新：已核对销售数据，正在制作问题分析页。
>
> 用户：第三页太复杂，简化一下，其他页继续。
>
> 助手：我会保留第三页的核心结论，简化呈现，其余页面继续制作。
>
> 助手：汇报已完成。下面是 PPT、页面预览和数据来源。

这条旅程不要求用户选择工具、填写版式表单或逐步批准内部操作。只有实际缺失的关键信息或授权范围变化才需要回应。示例是目标行为，不是当前能力验收结论。

### 1.1 默认自主完成

| 事项 | 默认行为 |
| --- | --- |
| 阅读本次已授权附件、分析数据、整理观点 | 自动执行 |
| 未指定页数、配色、版式、一般表达风格 | 根据用途自行选择，可随时被用户调整 |
| 大纲与设计方向 | 简短告知并继续；用户要求先审稿时等待 |
| 排版溢出、格式错误、普通布局调整 | 自动诊断和有限修正 |
| 用户明确修改某页，且目标唯一 | 自动生成修订版本，保留父作品，不重复确认原指令 |
| 主题无法从消息或资料确定，或修改目标存在多个候选 | 只追问影响结果的关键问题 |
| 新增联网、付费配图、资料外发或超出已接受预算 | 一次说明具体影响并取得授权；有效授权内不反复询问 |
| 删除原作品、不可恢复覆盖、影响未授权资料 | 执行前确认；默认新版本交付避免覆盖 |

品牌、管理层汇报等场景本身不强制增加审批步骤。事实冲突、重要假设无法确定、超出委托范围或用户明确要求审稿时才暂停。模型置信度用于辅助判断，不能作为权限依据。

### 1.2 范围与既有计划

会话入口覆盖普通聊天、资料问答、分析、Office 创建与修订。一条消息可包含连续目标，不强迫用户选择单一模式。PPT 是重点增强的交付形式，Word、Excel、图片理解、已交付文档问答和既有修订能力必须保留真实执行入口。

本文接续 [对话式逐页 PPT 与联网计划](CONVERSATIONAL_PPT_AND_MODEL_WEB_SEARCH_PLAN.md)。语义路由、自主设计和消息内「生产进度」以本轮及 2026-09-22 确认为准；来源证据、页面版本、恢复和预览一致性要求继续复用。进度放在当前助手回复中，可展开已执行步骤与逐页结果，不新增独立业务页面或必经控制面板。

负责人随后明确要求“优化文档，并执行”，当前任务已授权按本方案分批实施与本地验证。真实模型评测、企业资料外发和付费调用仍需已有有效授权与预算；实施授权不自动扩大这些范围。不重开历史阶段，不扩展到安装包或正式发布。

## 3. 会话架构：同一个 Agent 回复或行动

不采用每次先调用分类模型、再调用回答模型的固定双请求流程。用户不必显式切换 Agent。选定模型在一次会话响应中可以直接回答、提出必要问题，或请求执行工具。只有需要行动时才提交结构化语义计划和工具参数；普通聊天不强制等待完整文档计划。

### 3.0 核心控制模型：LLM 判断，本地原子工具执行

LLM 是任务控制器。它根据用户需求、已确认事实、已授权资料和工具目录，自主决定下一步是直接回答、追问、读取资料、分析数据、设计页面、渲染检查、局部修订还是结束任务；不要求所有任务遵循预设的 PPT 步骤，也不要求每次调用相同的工具序列。LLM 的每次行动都必须表达为受控的回复或结构化工具请求。

Application 提供本地原子工具。原子工具只完成一个可验证的职责，例如读取授权表格范围、聚合指标、创建或更新页面场景、生成图表、渲染预览、检查布局和登记发布候选。Application 在执行前校验 Schema、实体、授权、版本、依赖、预算、超时和取消状态；Platform 只执行通过校验的请求，并返回脱敏、结构化 Observation。LLM 根据 Observation 决定是否继续、调整参数、换用另一个已允许工具、向用户说明限制或结束任务。

LLM 可以改变工具调用顺序、页面构图和修正策略，但不能改变工具白名单、权限、预算、路径解析、服务商选择、凭证使用、正式作品登记或发布门禁。模型输出“已完成”不改变任务状态；只有本地文件、内容、布局、Hash、原子发布和 Work 登记全部通过后，任务才可进入正式完成。

```text
用户输入 / 对话中的补充与调整
                 │
                 ▼
Local Safety Gate：输入边界、停止按钮、明确取消、任务身份
                 │
                 ▼
Conversation Agent：流式回复 / 必要追问 / 语义计划与工具请求
                 │
                 ▼
Application：实体绑定、授权与版本校验、统一预算、有界调度
         │                    │                       │
         ▼                    ▼                       ▼
资料读取与分析工具     Word / Excel 既有执行器      PPT Designer 子流程
         │                    │                 内容、场景、视觉计划
         └────────────────────┴───────────────────────┤
                                                     ▼
                         Platform：写草稿 → 实际渲染 → 诊断
                                                     │
                              Observation → 有限修正 ┘
                                                     ▼
                         Application：核验结果 → 原子发布与 Work 登记
                                                     │
                                                     ▼
                         助手消息：真实进度、逐页预览、最终文件
```

每个实际步骤产生任务事件；工具观察结果回到 Agent，用户进度由事件投影生成。PPT Designer 是同一任务内的工具能力集合或受控子流程，不是另一个拥有独立权限的 Agent；它共享父任务的授权、取消、版本和预算，不能启动无限循环或绕过原子工具注册表。

### 3.1 与总体架构图对齐的职责边界

总体架构图中的 `Chat / Research / Document` 是能力和交付形式，不是三个互斥的路由分支。同一个 Conversation Agent 可以先回答结论，再调用本地资料检索工具，随后创建文档；Research 是受授权的上下文能力，Document 是任务目标，不能因为一次分类结果就截断复合请求。`TaskSpec` 必须至少包含目标、交付形式、已确认事实、约束、授权来源、预算快照、取消状态、候选实体和完成条件。

`Document Planner` 负责把 `TaskSpec` 和 Observation 转换为可更新的 `DocumentPlan`，再生成版本化 `Document IR`。PPT、Word、Excel 不作为拥有独立权限和循环的三个 Agent，而是共享同一任务运行时的格式适配器/执行器：各自负责 IR 映射、格式约束、渲染和文件校验，仍服从父任务的授权、预算、取消、版本和最大修正次数。任何所谓 `Patch Agent` 都只能是受限修正策略，不能绕过 Application 校验或自行发布。

执行链必须保留可恢复的 `Task Runtime` 和 Observation 回路：

```text
User Input
  → Local Safety Guard + Task Runtime
  → Conversation Agent（回复 / 追问 / 工具请求）
  → Application 校验与调度
  → Context / Research Tools 或 Document Planner
  → Document IR
  → Format Adapter（PPTX / DOCX / XLSX）
  → 结构预检
  → Platform Renderer
  → 文件结构、内容、布局与 Hash 校验
  → Render Preview
  → Visual QA
       ├─ PASS → 原子发布 → Artifact Registry → User Delivery
       └─ FAIL → 有界修正 → 重新渲染与完整 QA
```

`Local Safety Guard` 不是只在入口执行的过滤器；每次工具调用、写入、渲染和正式发布前都必须重新检查取消、授权、实体范围、revision、预算和状态。`Artifact Registry` 只能登记已经通过同一版本快照的本地文件校验、内容/布局检查、Hash、原子发布和 Work 登记门禁的产物。修正后必须重新执行渲染和全部 QA；连续相同诊断或达到修正上限时停止并返回可解释失败。

确定性 QA 分为两处：IR/页面生成前的结构预检，以及 Renderer 产物生成后的文件结构、内容、布局和 Hash 校验；Visual QA 必须使用与交付文件一致的实际渲染结果。任务事件、工具调用、Observation、页面 revision 和待发布状态需要由 Task Runtime 持久化，重启后先对账，不得依靠内存循环恢复或重复执行未知副作用。

### 3.1 本地前置处理保持简洁

本地只负责空输入、大小、格式、提交去重、会话身份和明确的停止动作。停止按钮直接控制当前 execution。仅对用户独立输入的明确取消短语，且只有一个确定目标时，支持不等模型的本地停止；“解释取消按钮”“不要取消”以及附件或引用中的“取消”不得误触发。复杂任务控制由 Agent 理解并由 Application 绑定目标。

权限撤销、取消和版本失效生效后，本地立即禁止新的相关调度与发布，并向可取消的模型请求和子进程传递信号。已经提交上游的工作可能继续计费，记录结果未知，不承诺“零延迟停止一切”或取消后绝无费用。

### 3.2 语义与状态分离

演进现有计划为版本化 `ConversationTaskPlan`，包含目标和可动态更新的子目标、交付形式、用户约束、可自主决定的偏好、来源引用、目标候选、必要追问、工具能力快照和预期完成条件。子目标表达任务依赖和完成条件，不规定唯一执行顺序；可同时表达“分析资料 → 回答结论 → 制作 PPT”，不使用互斥的 chat/create 分类截断复合请求。

模型从系统提供的候选 ID 中引用资料、作品和页面；Application 解析真实实体、项目归属、revision、允许范围及授权。语义不清时返回结构化诊断供模型澄清，不重新用业务正则猜用户意思。模型可以建议操作，不能自行授权读取、选择凭证、切换服务商、批准费用或登记 Work。

Application 状态机继续处理 `running / waiting_input / paused / cancelled / failed / completed` 等生命周期及合法迁移。移除语言猜测规则的同时保留任务持久化、并发和恢复机制。

### 3.3 模型能力不足与失败处理

依据连接、模型和协议的实际能力选择传输方式。原生 tool calling 优先；有可靠结构化输出能力时可采用受控 JSON 计划适配，两者进入同一校验与执行器。普通文本连接仍可聊天，但不能从自由文本猜出写文件指令。

模型不具备所需能力时，清楚说明限制并保留请求和已完成工作，提供切换到已配置可用模型的入口；不得静默换模型或退回正则执行业务。无网络、鉴权失败或模型不可用时，文件浏览、已保存作品打开和停止操作保持本地可用，新语义任务提示暂时无法继续。

## 4. 自主完成、必要追问和中途调整

### 4.1 需求完整性由语义与资料共同决定

“给老板做个销售汇报”不意味着必须逐项询问主题、受众、页数和风格。Agent 先检查消息、近期确认事实和已授权资料是否足够；有销售表时可以直接开始。只有缺少影响结果的关键事实时才追问，每次最多问 1—2 个关键问题，不重复问已知信息。

“做个 PPT”且没有上下文或资料时需要主题追问。新的模型主路由可以产生一次规划响应，但信息不足时不调用文档生成、搜索或配图工具。历史测试中此场景“模型调用必须为 0”的路由断言需要更新，保留“不擅自制作、不编造主题”的产品断言。

缺少企业业绩、产品功能等事实不能自行编造。可以先完成不依赖缺失事实的部分，再询问数据；采用定性说明时必须与证据相符，并告知用户影响。普通样式偏好不算阻断信息。

### 4.2 一次委托内自动完成

用户明确提出任务且资料使用范围已获授权后，读取、计算、规划、排版、渲染和检查连续进行。复用已选模型连接和已接受资源策略，不为每个普通文本轮次重复索取授权。联网和收费配图继续使用各自授权；“样式你决定”只授予设计选择权。

支持用户主动要求“先给大纲”“每页等我确认”或“直接做完”。默认直接做完，过程中可看见结果并介入。接受的自主范围保存到任务快照，不根据模型自述扩大。

### 4.3 插话不会丢掉正在做的任务

Agent 基于任务摘要、作品候选和用户所看到的版本解释插话：普通问答、补充资料、局部修订、全局目标变更或另起任务。普通问题可以回复而不重做 PPT；“第三页简化”只更新该页和必要依赖。全局目标改变时简短说明影响并更新计划，必要时暂停受影响部分。

页面修改绑定 `pageId + expectedRevision`。用户使用显示页码时，按其看到的版本映射；多个作品或版本确有歧义时才追问。任务内写操作按版本串行协调，旧执行晚到不能覆盖新指令。

自然语言授权和确认绑定实际用户消息、有效问题、taskId、计划版本、类型和范围。只有唯一有效目标时“可以”“继续”才作用于该问题；引用、材料文本、旧回复不能授权新操作。无需强制特定口令，也不能只凭模型输出 `authorized=true` 放行。

## 5. 工具合同与模型执行闭环

下表是能力划分，P0 与现有注册表完成映射后冻结具体工具 Schema，避免新旧两套执行权限。工具目录是 LLM 可选择的能力边界，不是必须逐项执行的流程清单。

| 工具能力 | 模型提出什么 | 程序负责什么 |
| --- | --- | --- |
| 项目资料检索、附件/作品读取 | 查询、候选 ID、需要的片段或页 | 本地 BM25 优先、归属、内容预算、Hash 和实际页映射 |
| 数据分析 | 类型化筛选、聚合、比较、指标与图表需求 | 受控运算、单位、数据来源、结果校验；不执行任意 Python/JS |
| Word / Excel 创建与修订 | 结构化内容或范围补丁 | 复用既有执行器、文件校验、父版本和发布门禁 |
| 联网检索 | 检索需求、已授权范围内的查询建议 | 区分原生搜索与应用工具，按能力、授权和协议执行 |
| PPT 创建 / 修订 | 整套目标、设计方向或目标页变更 | 进入可观察、可恢复的 Designer 子流程 |
| 页面场景更新、渲染、检查 | 场景或限定范围的修正建议 | 类型校验、真实 PPTX 生成与渲染诊断 |

`create_presentation` 可以作为模型易理解的高层入口，内部必须有逐页状态与检查点。模型不用为每个文本框、颜色或坐标逐次联网调用工具；同页元素可在一个场景请求中提交。最终发布由 Application 在门禁通过后推进，不以模型声称“完成”作为登记依据。

### 5.0 原子工具合同与组合工具边界

原子工具的粒度以“单一职责、可独立校验、结果可重放或可对账”为准。建议优先复用或演进以下能力：`read_source`、`read_table_range`、`aggregate_data`、`generate_chart`、`create_page_scene`、`apply_page_patch`、`render_preview`、`inspect_layout`、`publish_candidate`。工具可以一次处理同一页面的一组元素，避免把每个文本框拆成一次调用；但不得接受任意脚本、宏、原始 OpenXML、模型决定的文件路径或凭证。

每个工具合同至少固定：版本、输入/输出 Schema、前置条件、读取或写入范围、权限类型、副作用、幂等键、预期版本、超时、取消语义、预算消耗、失败码和安全审计字段。工具返回的 Observation 至少包含调用 ID、工具版本、状态、受影响实体或页面版本、来源引用、可继续行动的诊断和“结果未知”标记；不得把完整附件、原始网页、凭证、绝对路径或内部 Prompt 返回给模型或用户。

`create_presentation` 等高层入口只能是受控组合工具：它可以在一次请求中提交整套叙事或一个页面场景，由 Application 拆解为原子步骤并持久化检查点；组合工具不能绕过原子工具白名单、版本校验、局部修订、渲染诊断、发布门禁或 Work 登记。验收关注最终事实、来源、可编辑性、布局质量和安全边界，不要求每次得到完全相同的调用序列。

### 5.1 Provider 多轮协议

只在工具参数流完整接收、调用 ID 和 Schema 校验通过后执行，半截参数不产生副作用。保存必要的 assistant tool-call / tool-result 对应关系，以脱敏 Observation 继续模型回合；处理重复调用、非法 JSON、未知工具和流中断。自由文本中的“已完成”不能改变任务成功状态。

LLM 可以自主选择下一项工具；Application 依据工具声明的前置条件和实体依赖拒绝不满足依赖的调用，并对有副作用的写操作按实体和版本串行化。独立只读步骤只有在显式并发上限和结果合并规则存在时才允许并发。模型回合数、工具执行数、网络尝试和版式修正分别计数，共享任务总资源上限。Designer 子流程不能重新获得一份不受父任务约束的预算。

有副作用操作带幂等键和预期版本。重启后先对账执行记录；结果未知的收费请求不能自动重放。格式不合法可在限额内反馈诊断让模型重出，不能静默截断内容、改写数值或将错误参数全部替换为默认值后发布。

### 5.2 资料与联网

附件、网页和项目上下文作为不可信资料隔离进入模型，不能把其中指令当作用户授权。读取先走本地索引，按任务发送必要片段；确需读取整份授权文档时使用分块与上下文预算，不以“已添加附件”自动授权外部搜索服务取得全文。

模型处理资料的外发范围与搜索授权分别记录。连接、模型、资料范围、版本或预算变化时重新评估授权，仍在已接受范围内则复用。网页来源和引用用受控来源 ID 关联；普通正文链接或模型自述不能证明搜索执行过。

复用 [现有原生搜索能力](MODEL_NATIVE_SEARCH_DELIVERY.md)。未支持协议明确标记，不自动绑定独立搜索商、向量数据库或 embedding 服务。搜索未报告次数和费用保持未知，不能当成 0；硬预算无法执行时不能伪装为已受控。

## 6. PPT 设计自由与真实质量闭环

### 6.1 可组合的页面场景

Designer 先形成整套叙事和视觉方向，再输出页面场景。页面组件是可选设计起点，不能把能力封死在封面、KPI、对比、流程、卡片五种版式中。支持文字、形状、线条、分组、图片、表格和原生图表组合，模型可以提出坐标、尺寸、字号、颜色、间距、层级和裁切方式。

在现有 `PresentationPlan` 上增加版本化页面场景描述（Scene IR）：元素 ID/类型、内容或资源引用、几何信息、样式、父组、层级、阅读顺序、来源及保留条件。用类型化工具参数表达设计，不允许任意脚本、宏或原始 OpenXML 注入。字体和素材由运行时资源目录解析，路径与凭证留在 Platform。

页面越界、数值无效、文字不可读和资源失效需诊断；背景覆盖、装饰叠层和图片蒙版等有意重叠可以表达并验证，不能把所有相交都当成错误。文本、表格和图表尽量保持 Office 原生可编辑，不用整页截图代替可编辑 PPT。

### 6.2 先有成品证据，再修正

闭环为“场景 → 实际 PPTX → 页面渲染 → 结构与视觉诊断 → 修正场景 → 再渲染”。Bounding Box 只是其中一项，不能代替字体、截断、层级、密度、图表可读性、来源和整体一致性检查。

先做确定性修复，例如间距和可用字体回退；仍不满足时把限定范围的诊断交给 Designer。具备视觉能力的模型可接收已授权、必要的页面渲染图做视觉修正；不支持图像时只能使用真实结构诊断，不能把模型文字自评记为看过页面。修正超限保留草稿并说明问题，不交付虚假成功。

禁止为通过检查静默删除事实、改写数据、无限缩小文字或随意增页。明确要求固定页数时包含封面和结尾；通过内容重组和布局调整满足，确实不能兼顾时才向用户解释取舍。预览来自实际输出或经一致性验证的共享场景，不能用独立 HTML 美化效果冒充导出效果。

### 6.3 页面版本与恢复

每套保存 `deckId / deckRevision`，每页保存稳定 `pageId / pageRevision`、内容 Hash、场景、素材/主题依赖、实际页映射、预览和检查报告。状态为：

```text
pending → drafting → designing → rendering → checking → ready
                                      ↑          │
                                      └─ repair ─┘
分支：waiting_input / paused / cancelled / failed / stale
```

已检查页面可在整套完成前显示“草稿页已完成”。单页失败保留其他成果；重做只影响目标和必要依赖。重排更新页码和交叉引用，锁定页不被自动改写；全局调整涉及锁定页时说明影响。不靠整套重生成实现每次局部修订。

恢复时读取有效检查点并对账，不自动重新收费。最终使用同一 deckRevision 的完整页面快照核验内容、顺序、固定页数、来源、布局和 Hash，再经原子发布与 Work 登记。已登记但消息同步失败走 reconcile。

### 6.4 本批最小闭环：真实生成、有限布局修正与复验

本批在既有 Runner 上接入请求级修正端口，先使用受控 `DocumentOutline` 布局 Patch 作为过渡写入目标。该接线不等于所有原子工具已经统一写入 Document IR，也不等于聊天主链路已经启用 LLM 自主工具循环。最终实现和验收事实登记于第 12 节及 `PLANS.md` 顶部。

执行顺序为“生成临时 PPTX → 文件结构预检 → 实际 Office/PDF 渲染 → 结构化诊断 → 校验并应用布局 Patch → 重新生成 → 重新渲染与全部复验”。修正前后必须使用当前修订号；当前实现只接受稳定的 Outline `sectionIndex`，无法把实际物理页（封面、续页、结尾页）安全映射到 Outline 时直接拒绝，不能把上一轮渲染成功或只对 Outline 的检查当作新文件通过证据。

本批冻结以下边界：

- 每个请求最多修正 2 次，即初次生成加最多 2 次重新生成；继续继承父任务预算、取消状态与受控渲染器超时，修正端口本身也必须有等待上限。
- 诊断绑定当前 revision，包含真实诊断代码、严重程度和作用范围；页码、元素范围或几何信息只在实际取得时传递，不伪造定位。修正计划必须引用当前诊断，拒绝过期 revision、无效目标和非白名单操作。
- 本批只自动执行保持事实、数据、来源和非目标内容的布局调整。禁止为了通过 QA 改写正文或数值、删除内容、无限缩小字体、破坏固定页数；没有安全修正时停止并保留明确失败原因。
- 相同阻断诊断再次出现、没有有效变更、渲染器不可用、取消、超时、预算耗尽或未知副作用时停止；不增加新一轮模型、联网或收费请求来掩盖失败。
- 每轮修正、重新生成和复验都进入真实生产 Trace 与 Task Runtime 检查点。事件只显示修正次数、检查状态与安全诊断，不展示原始 Prompt、路径或附件全文。
- 只有最后一轮完整 QA 通过，才能执行该轮产物的 Hash、原子发布与 Work 登记；失败轮次不登记正式作品，不能复用旧轮次的校验结果。

验证必须覆盖修正后重新调用生成器和渲染器、最终登记只发生一次、重复诊断停止、次数上限、取消、超时、过期修订、越界目标及失败后禁止发布。使用合成渲染端口的回归只证明控制流程；真实 Office/PDF/PNG 夹具、文本框内部裁切、字体回退、非文本重叠和表格/图表可读性仍需独立取得证据，不能因此宣称完整 Visual QA 收口。

## 7. 生产进度与可靠事件

2026-09-23 最新实施状态：已新增独立于文本流的持久生产事件流，并将 `DocumentTaskRuntime` 接入文档 IPC 与真实本地生成事件；真实规划调用、正文模型调用、资料读取和本地文档编译/检查/发布位置均已接线。正式 PPT 现在必须经过配置的本地 Office/PDF 渲染器，文字越界、PPT 文本重叠、空页、页数不一致和无法完成文本检查会阻止 Work 登记；UI 默认展开本地与模型的交互时间线，Task Runtime 负责调用前检查点、Observation、恢复和 Work 登记门禁。旧 `task_progress` 仅保留兼容，当前生产使用独立 Trace，正文完成后继续接收本地文件事件。页面预览 IPC、自主 Agent 主循环在聊天主链路的完整接入、完整 PPTX 结构/视觉 QA 和自动修正仍未完成；详见 12.14、12.16、12.17。

用户可见名称固定为「生产进度」，不叫「制作过程」。按负责人最新明确要求，默认在助手消息内部展开实际执行时间线，按顺序流式追加每次本地→模型、模型→本地、本地工具的动作与结果；摘要只辅助定位当前状态，不能只显示“正在生产内容”或只折叠列出完成步骤。时间线展示真实开始、进行中、完成、失败、取消及时间；生成正文时同步展示模型已返回的可读标题、章节、段落、列表和表格内容，实际页面产物可用后再附逐页预览。不把工具参数表做成必填表单，不把模型思考原文、原始系统 Prompt 或完整附件作为执行链路。

生产进度只描述已发生的事实，例如“已核对销售数据”“正在制作第 3 页”“正在检查导出效果”。要体现的是与模型协作后的真实执行链路，不是原始模型交互日志：检索是否发生、读取哪些受控来源、做到哪一页、页面是否检查完成、费用是否已报告，均须有执行证据。所有页完成不等于正式作品已登记。

事件至少含 `eventId / taskId / executionId / sequence / stage / status / occurredAt / revision`，按需增加 `pageId / pageRevision / failureCode` 与安全计数。状态和待发布事件采用持久 outbox 或等价原子机制，至少一次投递、幂等消费；Renderer 去重、拒绝旧版本覆盖并支持快照后续订阅。

进度原位更新并节流，追问、授权和最终交付单独保存为助手消息。终态先落盘后通知，不因高频进度反复制造会话 revision 冲突；刷新、切换会话和重启后能重建。事件不返回凭证、绝对路径、原始请求体或思维链；进度摘要不重复灌入模型上下文。

## 8. 有界执行合同：在后台保证可控

不再把整个 PPT 任务限制为五步。资源策略按任务复杂度、页面数、已选模型能力和用户接受的预算形成有限快照，模型不得修改上限。普通用户无需填写这些内部参数。

实施前冻结各策略的有限数值，包括单请求/总超时、模型回合、工具调用、网络尝试、输入输出 Token、页面/元素资源量、修正次数和费用处理方式。不能只靠 Prompt 提醒。初始建议：每次无效结构最多重出 1 次、每页最多自动修正 2 次、相同诊断连续 2 次停止。其余数值由 P0 基线和实际连接约束确定，P1 接执行器前必须有可检验配置，禁止无限默认值。

| 阶段 | 结构化输入 → 输出 | 耗时与调用约束 | 失败与取消 |
| --- | --- | --- | --- |
| 会话理解 | 消息、任务摘要、候选实体 → 回复/问题/语义计划 | 模型单请求、总回合上限；普通聊天无额外分类调用 | `model_unavailable / plan_invalid / timeout`；取消后不调度工具 |
| 等待用户 | 有效问题和原始回复 → 绑定结果 | 不计主动执行耗时，问题及授权有有效期；用户消息驱动 | `ambiguous_reply / question_expired`；保留成果 |
| 本地检索与分析 | 受控来源、查询/运算 → 带来源结果 | 数据大小、片段量、单步耗时和总工具上限 | `source_missing / source_changed / analysis_failed`；终止可取消读取 |
| 联网 | 授权与能力快照 → 来源、执行及用量事实 | 单请求和网络次数有限；服务商内部不可控次数如实记录 | `authorization_required / search_unobserved / budget_exceeded`；撤销停止后续外发 |
| 整套与页面设计 | 需求、来源、页面状态 → DeckPlan/Scene IR | 统一模型回合、Token 和页面资源预算 | `design_invalid / source_conflict`；失效版本不入库 |
| 渲染和修正 | 场景及版本 → PPTX、预览、诊断 | 子进程超时、每页修正次数和总耗时 | `render_unavailable / layout_failed / repair_exhausted`；停止进程并保留检查点 |

### 12.18 2026-09-23 PPT QA 失败后的有限真实修正闭环
