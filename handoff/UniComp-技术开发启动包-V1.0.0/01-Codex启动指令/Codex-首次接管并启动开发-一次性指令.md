# UniComp｜Codex 首次接管并启动开发｜一次性指令

你现在接管 UniComp 项目的实际代码仓库。

## 一、先读取，不要立即重写代码

依次完整读取：

1. 仓库根目录现有 `AGENTS.md` 及所有目录级 `AGENTS.md`；
2. `handoff/UniComp-技术开发启动包-V1.0.0/README-技术人员先看.md`；
3. `handoff/UniComp-技术开发启动包-V1.0.0/01-Codex启动指令/AGENTS-项目级追加规则.md`；
4. `handoff/UniComp-技术开发启动包-V1.0.0/03-最终UI交接包-已解压/UniComp-AI-最终UI与开发交接包-V1.2.1/README.md`；
5. 该最终交接包的 `docs/00` 到 `docs/10`；
6. `tokens/UniComp-AI-Design-Tokens-V1.2.0.json`；
7. `manifests/resource-manifest.json` 和 `SHA256SUMS.txt`；
8. 全部权威高保真设计图；
9. `00-交接原件/docs.rar` 仅作为历史审计资料；
10. 当前仓库源码、现有文档、构建脚本、测试、CI、依赖和开发记录。

## 二、资料优先级

发生冲突时：

1. 项目负责人最新明确决策；
2. V1.2.1 最终 UI 与开发交接包；
3. 合并后的根目录 `AGENTS.md`；
4. 当前 active / frozen 正式文档；
5. 原始 `docs.rar`；
6. 旧代码、旧 UI 和旧归档。

旧代码和旧 UI 仅供审计，不得反向限制新版本。

## 三、禁止破坏

在完成接管审计前：

- 不删除旧代码；
- 不覆盖现有 `AGENTS.md`；
- 不迁移数据库；
- 不修改正式 UI 资源；
- 不批量重构；
- 不提交远端；
- 不加入多图参考、图片批量创作或视频批量创作；
- 不新增登录、会员、充值或云同步；
- 不把对话页做成可直接生成图片或视频的入口。

## 四、必须先完成的接管工作

### 1. 仓库审计

检查并记录：

- 技术栈和桌面框架；
- Windows / macOS 构建状态；
- 目录结构；
- 已实现页面；
- 已实现领域能力；
- 数据和文件存储；
- 任务中心；
- 服务商和模型接入；
- 密钥安全存储；
- 当前测试、lint、typecheck 和 build；
- 旧实现与 V1.2.1 的差距；
- 可复用代码和必须推倒重做的代码；
- 技术债、阻断项和风险。

### 2. 规则合并

把 `AGENTS-项目级追加规则.md` 与现有根目录 `AGENTS.md` 去重合并：

- 保留现有有效工程规则；
- 新产品与 UI 决策优先；
- 不覆盖目录级特殊规则；
- 记录合并内容和冲突解决。

### 3. 创建正式记录

在仓库适合的开发记录目录创建或更新：

- `00-接管审计报告.md`
- `01-当前实现与V1.2.1差距清单.md`
- `02-开发实施总计划.md`
- `03-技术风险与验证计划.md`
- `04-页面实现与权威设计图映射.md`
- `05-测试与验收总表.md`
- `CHANGELOG.md` 或现有更新日志

不得创建重复的文档体系；如果仓库已有对应文件，更新现有文件。

### 4. 建立执行计划

创建根目录 `PLANS.md` 或使用仓库已有等效执行计划，至少分为：

- 阶段 0：接管审计与工程基线；
- 阶段 1：桌面应用壳、导航、主题和 Design Tokens；
- 阶段 2：本地项目、草稿、文件、作品和任务领域；
- 阶段 3：对话、项目、任务中心、作品库全局页面；
- 阶段 4：模型与服务商、BYOK、动态能力和安全存储；
- 阶段 5：图片创作页面和图片任务链路；
- 阶段 6：视频创作页面和视频任务链路；
- 阶段 7：视频基础编辑本地引擎；
- 阶段 8：本地设置十个分类；
- 阶段 9：跨平台、故障恢复、安全、性能和完整验收；
- 阶段 10：Windows / macOS 打包与发布准备。

每个阶段必须包含：

- 输入文档；
- 实现范围；
- 不实现范围；
- 验收条件；
- 测试命令；
- 产出文件；
- 回滚方式。

## 五、执行当前仓库基线验证

运行当前仓库真实可用的：

- 依赖安装或依赖完整性检查；
- lint；
- typecheck；
- unit test；
- integration test；
- build；
- 桌面端开发构建或 smoke test。

不要编造命令。先根据仓库脚本确定命令，再执行并记录真实结果。

## 六、没有阻断项时，直接开始阶段 1

完成以上审计和计划后，如果不存在必须由项目负责人决策的阻断项，直接开始：

> 阶段 1｜桌面应用壳、最终左侧导航、主题系统、Design Tokens 和基础组件层

阶段 1 只实现：

- Windows / macOS 共用桌面壳；
- 最终八项一级导航；
- 图片和视频创作二级导航展开规则；
- 深色 / 浅色主题；
- Design Tokens 接入；
- 基础按钮、输入、卡片、状态、弹窗和布局组件；
- 路由与页面占位骨架；
- 不实现具体生成业务；
- 不修改权威设计图。

阶段 1 完成后必须：

- 运行验证；
- 截图或生成可核对的本地预览；
- 更新开发记录；
- 对照设计规范自检；
- 明确下一阶段入口；
- 不擅自继续跨阶段大规模开发。

## 七、遇到阻断项时

只有以下情况才停止并向项目负责人提问：

- 最终资料内部仍存在无法根据优先级解决的实质冲突；
- 代码仓库缺失关键目录或无法构建；
- 技术栈尚未确定且会影响长期架构；
- Windows / macOS 方案存在必须二选一的重大分歧；
- 第三方许可证或安全问题阻止实现；
- 需要真实账号、密钥、证书或硬件才能继续。

其他普通工程判断由你依据文档和现有代码处理，不要反复要求确认。

## 八、本轮回复格式

先回复：

1. 已读取文件清单；
2. 仓库现状摘要；
3. 基线验证结果；
4. 发现的冲突与处理；
5. 新建或更新的文档；
6. 阶段 1 是否已经开始；
7. 已修改文件；
8. 已运行测试；
9. 当前阻断项；
10. 下一步。

然后实际执行上述工作，不要只输出建议。
