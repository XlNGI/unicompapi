## 1. 文档目的

本文是 UniComp AI UI/UX 设计阶段的统一输入，不是最终视觉规范，也不是前端实现说明。

本文用于保证产品负责人、UI 设计、交互设计、技术负责人和 Codex 对以下内容采用同一口径：

- UniComp AI 是什么、不是什么；
- 首版核心用户和高频任务是什么；
- 图片与视频两条主线如何组织；
- 项目、素材、上下文、提示词、任务、作品、模型之间是什么关系；
- 哪些产品流程已经冻结，可以进入设计；
- 哪些模型、费用和平台细节尚未实测，UI 不得写死；
- 每个核心页面必须覆盖哪些正常、空、失败、恢复和授权状态；
- 设计成果达到什么标准后，才能提请冻结并交给前端实现。

本文不修改 15 份已冻结的 UniComp AI 产品文档。若设计过程中发现上游规则冲突、遗漏或不可实现项，必须进入需求变更流程，不能由设计稿自行改变产品规则。

## 2. 阶段结论与事实边界

### 2.1 已确定

1. UniComp AI 是本地优先的桌面 AI 视觉创作工作台；
2. 图片创作与视频创作是 V1.0 的两条核心主线；
3. 产品支持 Windows 与 macOS，两个平台保持一致的信息结构、视觉语言和核心流程；
4. 用户不需要 UniComp 账号即可使用本地能力和配置自己的服务商；
5. 在线调用优先采用 BYOK，由受控本机网络层直连用户选择的服务商；
6. 图片、视频、提示词增强、任务中心、作品库、模型管理、隐私授权和异常恢复的产品规则已经冻结；
7. UI 视觉与交互设计可以启动；
8. UI 冻结前不得启动正式前端页面开发。

### 2.2 官方资料与方案层面已确认，但仍待真实验证

- 候选图片与视频服务商存在完成 V1.0 目标能力的接口路径；
- 桌面直连、系统级凭据保护、异步任务恢复、本地原子保存等存在可行技术路径；
- Windows 与 macOS 存在候选安全存储、目录权限和应用分发方案；
- 不同服务商在参数、状态、取消、结果返回、费用和数据政策上存在明显差异。

### 2.3 尚未确认，UI 不得写成固定事实

- V1.0 首批正式支持的服务商和模型名单；
- 各模型实际可用的分辨率、尺寸、时长、数量、参考图上限和文件限制；
- 各模型是否支持远端取消、任务恢复、幂等提交或结果重取；
- 生成耗时、排队时长、成功率、质量等级名称和真实费用；
- 失败、取消、超时和重试的实际账单结论；
- Windows/macOS 最低版本、硬件架构、沙盒、目录和权限细节；
- 桌面 BYOK 对每一家候选服务商的最终政策与法律结论；
- 自定义兼容接口的最终安全范围；
- 本地推理在目标 macOS 与 Windows 设备上的性能边界。

### 2.4 设计表达规则

对于第 2.3 节的内容，设计稿必须使用以下方式表达：

- 以“能力声明”控制参数是否显示、可用、受限或未知；
- 使用动态字段和状态容器，不把候选值当最终固定值；
- 服务商和模型选择器必须能显示“已验证、用户声明、受限、未知、不可用”等状态；
- 价格不可确认时显示“费用未知”或“以服务商账单为准”，不得虚构估价；
- 取消能力未知时不得显示确定的“可取消”承诺；
- 生成时间未知时使用真实任务状态与已等待时间，不显示虚假百分比；
- 原型示例中的模型名称和数值必须标注“示例数据，不代表正式支持”。

## 3. 产品定位与体验目标

### 3.1 正式定位

UniComp AI 是面向内容创作者、电商与营销人员、设计与视觉人员及小型创作团队的本地 AI 视觉创作工作台。用户在一个项目中组织素材和上下文，完成图片、视频创作，透明确认最终提示词与发送对象，管理异步任务，并把结果可靠地保存为本地作品。

### 3.2 明确不是什么

UI 不得把 UniComp AI 设计成：

- 以聊天消息流为主体的普通 AI 聊天软件；
- 以数据表格、统计卡片和多级菜单为主体的传统后台；
- 以请求参数、JSON、HTTP 调试和开发者术语为主体的 API 工具；
- 以强制登录、会员、充值或 UniComp 云端为入口的商业平台；
- 只展示结果而隐藏服务商、发送内容、费用来源和任务状态的黑盒；
- 模仿某一家模型服务商、剪辑软件或图片软件的复制品。

### 3.3 核心体验目标

1. **创作优先：** 打开项目后能快速进入图片或视频创作，不被设置和技术信息打断；
2. **内容优先：** 素材、画面、视频预览和创作结果占据视觉中心，参数为内容服务；
3. **过程透明：** 用户能看见原始输入、系统补充、最终提示词、接收方、模型和费用状态；
4. **可恢复：** 排队、生成、下载、失败、过期、断网和重启后都能找到真实任务状态与下一步；
5. **本地可信：** 清楚区分本地操作与外部发送，作品是否已保存到本地必须明确；
6. **能力驱动：** UI 根据当前模型能力动态呈现可用参数，不让用户提交模型明确不支持的组合；
7. **新手易用、进阶可控：** 默认路径短，基础参数先出现，高级参数按需展开；
8. **批量不混乱：** 每个子任务状态、结果、失败和费用相互独立，可批量查看但不丢失个体事实。

## 4. 用户优先级与核心场景

### 4.1 用户优先级

1. 内容创作者、自媒体与短视频创作者；
2. 电商、品牌与营销内容人员；
3. 设计与视觉创作人员；
4. 中小工作室与进阶模型用户。

设计文案以创作语言为主，必要的模型和服务商信息采用可解释的辅助层，不默认要求用户理解 API、异步任务、状态码或模型参数差异。

### 4.2 V1.0 核心场景

| 场景 | 用户目标 | 主要输入 | 成功结果 |
| --- | --- | --- | --- |
| 图片生成 | 从文字或参考图获得图片 | 提示词、上下文、参考图、模型能力参数 | 图片已可靠保存，可比较、继续编辑或再次生成 |
| 图片识别 | 理解图片内容并继续创作 | 单图或多图、识别任务、问题 | 可编辑、可选择、带不确定性标记的识别结果 |
| 图片编辑 | 保留指定内容并修改局部或整体 | 原图、修改要求、保留要求、可选蒙版 | 新版本作品，不覆盖原图，可对比和回退 |
| 图片转提示词 | 从图片得到可编辑创作描述 | 图片、目标用途、输出结构 | 结构化提示词草稿，确认后才能进入新任务 |
| 多图参考 | 组合人物、商品、场景、风格等参考 | 多张图片及每张用途 | 发送范围清楚、用途明确的生成任务 |
| 文生视频 | 将短文本、长文本、脚本或营销内容转成视频 | 文本、上下文、镜头草稿、参数 | 异步任务完成并保存为本地视频作品 |
| 图生视频 | 让一张或多张图片产生符合要求的运动 | 参考图、图片用途、运动要求、提示词 | 视频结果与来源图、提示词和任务可追溯 |
| 批量创作 | 一次创建多个图片或视频任务 | 多条草稿、共享设置、子任务差异 | 每个子任务独立跟踪、失败、重试和保存 |
| 作品管理 | 找到、比较、导出和继续使用本地结果 | 筛选条件、项目、版本关系 | 文件与元数据一致，版本来源清楚 |
| 多模型选择 | 在已配置模型中按能力、质量或成本选择 | 任务类型、能力要求、用户偏好 | 选择理由透明，不发生静默切换 |

## 5. 核心对象与关系

设计必须清楚区分以下对象，避免将任务、作品、文件和项目混为一体：

| 对象 | 含义 | UI 中必须可见的关键事实 |
| --- | --- | --- |
| 项目 | 一次或一组持续创作的本地容器 | 名称、上下文、素材、任务、作品、最近活动 |
| 素材 | 用户导入或从作品复用的图片、视频、文本等输入 | 类型、来源、是否选中、用途、是否会外发 |
| 上下文 | 用户明确选择用于当前创作的人物、品牌、场景、脚本等信息 | 选择范围、来源、可删除、是否进入最终提示词 |
| 创作草稿 | 尚未正式提交的创作配置 | 输入、素材、提示词层、参数、模型、授权状态 |
| 提示词三层 | 原始输入、系统补充、最终提交内容 | 分层展示、来源、可编辑、可移除、最终确认 |
| 服务商 | 实际接收请求并提供能力的主体或接入渠道 | 名称、类型、接收地址类别、验证状态、数据离开本机提示 |
| 模型 | 服务商下具体执行能力的模型 | 能力、限制、状态、验证来源，不用营销名称代替事实 |
| 任务 | 一次实际提交及其远端和本地处理过程 | 状态、阶段、服务商、模型、费用状态、操作、恢复信息 |
| 作品 | 已成功保存到本地并登记的图片或视频结果 | 文件状态、来源任务、版本关系、提示词、模型、导出操作 |
| 文件 | 本地磁盘上的真实媒体或项目数据 | 路径状态、存在性、完整性、丢失/损坏/迁移状态 |

核心闭环：

`项目与素材 → 创作草稿 → 提示词确认 → 发送与费用确认 → 任务中心 → 结果处理与本地保存 → 作品库 → 继续编辑或再创作`

设计时必须保证：远端返回成功不等于作品完成；只有结果完成本地保存和登记后，才能显示“作品已完成”。

## 6. 建议信息架构输入

本节给出 UI 设计必须覆盖的功能域和推荐组织方式。最终导航名称、分组和层级在《信息架构与导航设计》中确定，不能反向删减上游能力。

### 6.1 一级功能域

1. **项目与最近创作：** 创建项目、打开最近项目、查看近期任务与作品；
2. **创作工作区：** 在项目内完成图片和视频创作；
3. **任务中心：** 统一查看图片、视频、批量和下载任务；
4. **作品库：** 管理已保存到本地的图片与视频作品；
5. **模型与服务商：** 配置 BYOK、本地/局域网/自定义接口、测试连接和查看能力状态；
6. **本地设置：** 存储、备份、迁移、代理、安全、外观和应用设置。

### 6.2 创作工作区二级能力

- 图片生成；
- 图片识别；
- 图片编辑；
- 图片转提示词；
- 多图参考；
- 文生视频；
- 图生视频；
- 批量图片与视频任务；
- 基础视频编辑与导出；
- 上下文与素材管理；
- 提示词增强和最终提交确认。

### 6.3 组织原则

- “对话”只作为创作辅助，不作为一级产品骨架；
- 图片和视频是创作模式，不应分裂成互不相干的两个应用；
- 项目提供上下文和素材连续性，任务中心提供过程连续性，作品库提供结果连续性；
- 模型配置是支持能力，不抢占创作页面的主要视觉位置；
- 频繁参数放在当前任务附近，高级和模型专属参数按需展开；
- 不把全部状态和设置塞进单个页面，也不为每个细小动作创建独立页面。

## 8. 核心页面设计输入

### 8.1 项目入口与最近创作

必须包含：

- 新建项目和打开本地项目；
- 最近项目、最近任务、最近作品；
- 项目封面或最近作品预览；
- 明确区分“继续创作”“查看任务”“打开作品”；
- 没有项目、项目路径失效、项目数据损坏、外置盘断开等状态；
- 不使用账号登录作为首页门槛。

### 8.2 图片创作工作台

必须容纳：

- 创作模式切换：生成、识别、编辑、图片转提示词、多图参考；
- 原始输入、上下文选择和提示词增强入口；
- 主图、参考图、每张图片的用途和是否发送；
- 当前服务商与模型、能力与验证状态；
- 基础参数与高级参数的渐进展开；
- 提交前检查、费用/未知、接收方和授权；
- 结果预览、多个版本、原图对比、继续编辑、重做和保存状态；
- 空结果、生成中、部分结果、失败、过期链接、下载失败和本地文件异常。

图片编辑不得覆盖原图。识别结果必须能区分可见事实、模型推断、不确定、无法识别和用户修改。多图参考必须让每张被发送的图片拥有明确用途。

### 8.3 视频创作工作台

必须容纳：

- 文生视频与图生视频；
- 短文本、长文本、故事、脚本和营销文案输入；
- 长文本生成多个可编辑镜头/任务草稿，支持合并、删除、排序和逐条确认；
- 主体、动作、场景、镜头、风格、光线、色彩、节奏、用途和约束；
- 参考图用途、运动要求和可编辑的图片理解结果；
- 原始模式、智能优化、上下文增强、长文本转换等提示词模式；
- 模型能力驱动的视频参数；
- 异步任务提交、等待、结果处理、下载、本地保存和继续创作；
- 基础视频编辑入口，但不得伪装成专业剪辑软件。

视频任务不得显示虚假进度。若服务商只返回排队/处理中等粗粒度状态，UI 应显示真实阶段、已等待时间、最近查询时间和可执行操作。

### 8.4 提示词增强与最终确认

必须同时展示：

1. 用户原始输入；
2. 系统补充内容；
3. 最终提交提示词。

每项系统补充都要标明类别、来源、是否可编辑和可移除。最终提交内容需要清晰可见、可复制、可编辑、可恢复原始输入。翻译和模型格式转换也属于系统补充，不能隐藏。

提示词增强状态与实际生成任务状态必须分开。增强完成不等于已提交，长文本拆分完成不等于已创建任务。

### 8.5 外发与费用确认

提交前确认至少显示：

- 真实服务商、接入渠道、模型与验证状态；
- 发送用途；
- 原始输入、系统补充、最终提示词；
- 将发送的上下文、图片、视频、蒙版、脚本和其他素材；
- 参数和批量数量；
- 预计费用、费用未知或以服务商账单为准；
- 数据将离开本机、可能跨境或处理地区未知的状态；
- 同服务商自动重试授权范围；
- 本次确认按钮和返回修改入口。

同一服务商的首次配置授权不能替代本次发送确认。跨服务商发送、重试或切换必须暂停并重新确认。外部提示词增强服务若与生成服务不同，必须分别展示接收方和费用。

### 8.6 任务中心

任务中心必须覆盖统一任务状态：

- 草稿；
- 等待确认；
- 等待提交；
- 上传中；
- 排队中；
- 提交中；
- 生成中；
- 结果处理中；
- 下载中；
- 已完成；
- 部分完成；
- 已失败；
- 已取消；
- 可重试；
- 已过期；
- 需要用户处理。

每个任务至少显示任务类型、项目、创建时间、服务商/模型、当前阶段、结果数量、费用状态和当前可执行动作。批量任务必须显示总数、进行中、完成、失败、取消和需要处理的子任务数量，并允许进入单个子任务。

“取消”必须区分停止本地等待、已请求远端取消、远端确认取消和无法确认远端状态。重试创建新执行记录，不能覆盖原任务事实。

### 8.7 作品库

必须包含：

- 图片与视频统一浏览，并可按项目、类型、时间、模型、标签、收藏等筛选；
- 缩略图/预览、名称、来源任务、创建时间和本地文件状态；
- 作品详情中的提示词三层、服务商/模型、参数、参考素材和来源任务；
- 父子版本和同源并列版本关系；
- 重命名、收藏、导出、继续编辑、再次生成、删除和批量操作；
- 文件丢失、损坏、移动、外置盘断开、预览失败和元数据仍在等状态；
- 删除作品与删除项目、任务、原素材之间的边界提示。

### 8.8 模型与服务商管理

必须区分服务商、模型与能力三层，并区分：

- 国内在线服务商；
- 海外在线服务商；
- 本机模型；
- 局域网模型；
- 自定义远程兼容接口。

每项配置至少显示：名称、接口类别、凭据状态、连接状态、身份核验状态、能力来源、上次验证时间和可用限制。Key 只允许输入、替换、测试和删除，常态只显示掩码与状态，不提供读取明文操作。

连接测试成功不得显示成“所有能力已验证”。自定义接口必须显示真实地址类别和风险，不能冒充官方服务商。

## 9. 动态能力与参数设计

### 9.1 能力状态

设计需支持至少以下状态：

- 已验证支持；
- 官方资料支持，待实测；
- 用户声明；
- 受账户/地区/版本限制；
- 当前不可用；
- 明确不支持；
- 未知。

### 9.2 参数呈现

- 基础参数先显示，高级与模型专属参数按需展开；
- 切换模型时重新计算可用参数，保留用户意图但不能静默提交无效值；
- 不支持的参数优先隐藏；需要解释时置灰并说明原因；
- 参数变化导致费用、接收方或素材范围变化时，原授权失效并返回确认；
- 模型名称、枚举值、上限、默认值和计费单位全部来自后续能力配置，不写死在设计规范或前端页面；
- 未确认值可以在原型中使用示例，但必须有统一的“示例数据”标识。

### 9.3 模型选择

模型选择器需要帮助用户理解“为什么可选、为什么推荐、为什么不可用”，但不得默认推销 UniComp API 或某一家服务商。用户手动指定模型后，系统不应静默更换。

## 10. 状态、异常与恢复设计矩阵

每个核心页面必须至少提供以下设计稿或可复用状态组件：

| 类型 | 必须覆盖的状态 |
| --- | --- |
| 初始与空状态 | 未建项目、无素材、无草稿、无任务、无作品、未配置任何模型 |
| 加载与校验 | 读取本地项目、校验素材、连接测试、能力同步、提示词增强中 |
| 提交前 | 参数不支持、素材超限、缺少 Key、余额/权限未知、授权失效、费用未知 |
| 网络与外部服务 | 离线、DNS、代理、证书、地区限制、限流、服务不可用、响应无法确认 |
| 异步任务 | 上传、排队、提交、生成、结果处理、下载、长期等待、状态查询失败 |
| 终态 | 完成、部分完成、失败、取消、过期、需要用户处理、可重试 |
| 本地文件 | 磁盘满、只读、占用、目录无权限、文件丢失、文件损坏、外置盘断开 |
| 安全与凭据 | Key 无效、Key 已删除、接口地址变化、证书不可信、目标身份未知 |
| 批量 | 部分上传失败、部分生成失败、部分保存失败、混合费用状态、逐条重试 |

错误信息必须回答：发生在哪一步、哪些内容已经成功、是否可能已计费、是否会重复发送、用户下一步能做什么。技术错误码可在详情中提供，但不能作为唯一用户提示。

## 11. 授权、隐私与本地可信设计

### 11.1 本地与外部操作分层

以下操作默认是本地行为，不应频繁弹出外发确认：项目整理、素材分类、作品预览、本地编辑草稿、重命名、收藏和本地筛选。

以下操作必须在界面上清楚提示外发事实：在线提示词增强、图片识别、图片/视频生成、上传参考素材、远端重试、跨服务商切换和自定义远程接口请求。

### 11.2 授权层级

- 服务商首次配置授权；
- 每次真实发送前的任务级确认；
- 批量任务明确范围的批次授权；
- 同服务商自动重试的次数与费用范围授权；
- 跨服务商每次重新确认；
- 单独的外部提示词增强服务确认。

### 11.3 交互原则

- 授权信息与创作内容放在同一确认上下文中，避免用户只看见抽象“同意”；
- 接收方、素材范围、费用和跨境状态发生变化时清楚说明变化原因；
- 不使用预勾选同意、不用模糊文案扩大授权、不以关闭弹窗代表同意；
- 允许返回修改，不因返回而丢失草稿；
- Key、完整请求、素材和敏感路径不得出现在普通日志、截图示例或诊断界面；
- 删除本地 Key 时提示用户：这不等于服务商侧 Key 已撤销。

## 12. 视觉方向输入

本节只冻结视觉目标，不冻结最终颜色、字体、图标库或像素尺寸。最终令牌在《视觉系统与设计令牌》中确定。

### 12.1 视觉性格

- 专业、克制、可信；
- 以创作内容和预览为主，不以装饰为主；
- 有现代 AI 创作工具感，但不使用夸张霓虹、过度渐变和低可读性的“科技感”；
- 让图片和视频作品成为主要色彩来源，界面容器保持稳定和安静；
- 能长时间使用，适合桌面生产力场景。

### 12.2 布局原则

- 桌面优先，支持可调整的工作区；
- 创作内容区拥有最大视觉权重；
- 主导航、素材/项目、创作画布、参数/状态采用清晰分区，但不强制所有页面同时出现三栏；
- 主要操作在当前任务附近，避免跨页面寻找“生成”“确认”“保存”；
- 单个界面只保留一个最明确的主操作；
- 高级参数、技术详情、错误证据和元数据采用渐进披露；
- 小窗口和高缩放比例下允许面板折叠，不丢失主要操作和状态。

### 12.3 主题与语义色

- 同时考虑浅色与深色主题，不把深色视为唯一“AI 感”；
- 主色仅用于主操作与关键选中状态；
- 成功、警告、失败、处理中、未知、需要用户处理必须有独立语义，不只依赖颜色；
- 作品预览周围避免大面积高饱和背景，减少对图像判断的干扰；
- 不在本阶段预设紫色、蓝色或任何特定品牌色为最终方案。

### 12.4 字体、图标与动效

- 优先使用适合中英文混排和桌面长时间阅读的无衬线字体方案；
- 文字层级、数字、状态和参数必须清晰，不用代码字体制造技术感；
- 使用一致的矢量图标体系，不使用 Emoji 充当正式功能图标；
- 动效用于状态变化、面板过渡、任务反馈和版本对比，避免无意义循环动画；
- 常规交互动效宜保持短促，并支持系统减少动态效果设置。

## 13. 桌面、跨平台与无障碍要求

### 13.1 Windows 与 macOS

- 核心信息结构、页面命名、任务状态和产品规则一致；
- 允许窗口控制区、快捷键标记、系统选择器和权限提示遵循平台习惯；
- 未完成原型前，不在设计稿中承诺具体系统目录、权限弹窗或沙盒行为；
- 外置盘、目录失效和权限变化必须有可恢复界面；
- 用户换设备或迁移项目时，默认不迁移 API Key 的事实需要明确说明。

### 13.2 键盘与焦点

- 所有核心操作必须可通过键盘到达；
- 焦点状态必须清晰可见，不得因视觉简洁而移除；
- 支持常用桌面快捷键的设计预留，但最终组合需避开 Windows/macOS 系统冲突；
- 模态框打开后焦点进入，关闭后返回触发位置；
- 长列表、参数面板和素材网格需要合理的键盘导航顺序。

### 13.3 可读性与操作尺寸

- 正文和控件文字满足常见可读性与对比度要求；
- 颜色不是状态的唯一表达；
- 主要可点击区域按桌面触控板和高分屏环境保留足够命中范围；
- 错误提示靠近对应字段，并在页面级提供汇总和恢复入口；
- 上传、提交和付费操作必须防止连续点击导致重复执行。

## 14. 设计系统必须包含的组件

后续组件规范至少覆盖：

- 应用外壳、主导航、项目切换器；
- 创作模式切换、分段控件、标签和面包屑；
- 素材卡、素材选择器、上传区、用途标签和发送范围标记；
- 提示词编辑器、三层对比、补充项、来源标记和恢复原始；
- 模型选择器、服务商标记、能力状态、限制说明和连接状态；
- 基础/高级参数面板、动态字段、未知/受限状态；
- 提交确认摘要、费用状态、跨境/外发提示和授权操作；
- 任务卡、状态时间线、批量汇总、错误详情和恢复操作；
- 图片/视频预览、版本对比、父子关系、缩略图和全屏查看；
- 作品卡、筛选、排序、批量操作、文件状态和导出；
- 空状态、骨架加载、内联错误、通知、对话框、抽屉和确认条；
- Key 输入、掩码状态、连接测试、自定义接口类别和危险操作；
- 工具提示、快捷键提示、进度/等待反馈和系统通知状态。

每个组件至少定义默认、悬停、按下、焦点、选中、禁用、加载、错误和只读状态；不适用的状态需明确说明。

## 15. 设计交付顺序

1. **信息架构与导航：** 确认一级功能域、项目内结构、页面清单和跨页面关系；
2. **核心任务流：** 完成图片、视频、提示词确认、外发授权、任务恢复和作品继续创作流程；
3. **低保真交互：** 验证信息密度、面板关系、操作顺序和异常回路；
4. **视觉方向探索：** 提供少量有明确取舍的视觉方案，由产品负责人选择；
5. **高保真核心页面：** 先完成第 7.1 节页面及关键状态；
6. **设计系统：** 冻结颜色、字体、间距、栅格、组件、图标和动效；
7. **完整状态与第二批页面：** 覆盖模型、设置、批量、基础编辑和跨平台差异；
8. **可感知验收：** 以可点击原型、页面导出和状态对照进行实际预览；
9. **设计冻结：** 解决评审问题并更新版本，作为前端实现唯一依据。

不能先画一张“漂亮首页”后让其他页面自由延伸。图片创作、视频创作、任务中心和作品库必须在同一信息架构与设计系统下共同验证。

## 16. UI 设计验收标准

设计阶段完成至少满足：

### 16.1 产品一致性

- 没有把对话、后台、API 调试或账号体系变成产品主线；
- 图片和视频两条核心创作线清晰；
- 项目、任务、作品和文件没有混淆；
- 提示词三层、服务商、模型、发送内容和费用状态透明；
- 长文本先生成可编辑草稿，不自动提交；
- 跨服务商发送必须重新确认；
- 远端成功与本地作品完成严格区分。

### 16.2 真实能力边界

- 未实测的模型名称、参数、费用、取消和预计时长没有被写成产品承诺；
- 参数由能力状态驱动；
- 未知、受限、用户声明和已验证状态在视觉上可区分；
- 原型示例数据有统一标识；
- 没有虚假进度、虚假取消成功或虚假费用结论。

### 16.3 流程完整性

- 每条核心流程从输入、确认、提交、等待、本地保存到继续创作完整闭环；
- 失败、断网、重启、过期、部分完成和需要用户处理有明确恢复路径；
- 批量任务可以查看汇总，也能追踪单个子任务；
- 不因返回修改、切换页面或重启而无故丢失草稿和任务事实。

### 16.4 视觉与交互质量

- 视觉内容是核心，界面不是传统后台或过度装饰的科技面板；
- 主操作清晰，基础与高级参数分层；
- 键盘、焦点、对比度、错误提示和防重复提交满足桌面可用性；
- Windows 与 macOS 共享产品结构，并对平台差异留出正确位置；
- 组件和状态可复用，不依靠逐页临时设计；
- 设计成果经过实际预览或可点击原型验收，不以文件存在代替完成。

## 17. 本阶段待产品负责人确认

1. 是否批准本文作为 UniComp AI 后续 UI 设计的统一输入；
2. 是否批准第 6 节的一级功能域作为信息架构设计起点；
3. 是否批准第 7.1 节的八类页面作为首批高保真设计范围；
4. 是否同意视觉方向先探索“专业、克制、内容优先”的少量方案，而不预设最终品牌色；
5. 是否同意 UI 设计与真实账号/跨平台原型并行，但每次模型细节冻结都必须引用实测结果。

未确认上述事项前，可以进行信息架构草案和低保真研究，不得把本文升级为“已冻结”或交给前端开发。
